## 3. FTL 알고리즘 분류

### 3.1 Addressing mapping

#### 3.1.1 Sector mapping
* 가장 naive한 FTL 알고리즘
* 모든 logical sector가 대응하는 physical sector에 1:1로 매핑됨
* logical sector가 m개면 logical-to-physical 매핑 테이블의 row 크기도 m

![섹터 매핑 예](/assets/img/posts/FTL_2/image.png)
* 가정: 1 block = 4 page, 총 16 physical page (= 16 logical sector 존재)
* 'write(9, A)': 데이터 'A'를 lsn 9에 써라
    * 매핑 테이블 기준 lsn 9 -> psn(physical sector number) 3
    * psn 3에 이전에 쓰인 데이터가 없으면 -> 그대로 psn 3에 'A' 씀
* **다른 경우**: FTL이 empty physical sector 위치를 찾아 거기에 쓰고 매핑 테이블 조정
    * empty sector가 없으면 -> victim block 선택 -> victim block의 valid data를 spare block으로 copy -> 매핑 테이블 갱신 -> victim block erase (victim block은 spare block이 됨)
        * victim block: valid data와 invalid data가 섞여 있는 block. 이걸 erase해서 재활용.
            * valid data: 매핑 테이블이 현재 가리키고 있는, 최신이고 실제로 유효한 데이터
            * invalid data: 예전에 쓰였지만 이후 다른 위치에 새 값이 쓰이면서 더 이상 매핑 테이블이 가리키지 않게 된, 쓸모없어진 옛날 데이터(안 쓰지만 물리적으로 메모리에 남아있음)
        * spare block: flash memory 어딘가에 미리 확보되어 있는, 완전히 비어있는 block. victim block을 erase하기 전에, 그 안의 아직 valid data를 여기로 옮겨놓는 temp 역할.
* 2.2의 기능2 **Power-off recovery**: 2개
    1. 매핑 테이블을 flash memory에 저장
    2. 매 write 연산마다 sector area의 spare area에 logical sector number를 기록
        * sector area(=data area): 실제 사용자 데이터가 저장되는 공간
        * spare area(=OOB area, out-of-band area): sector area에 딸린 작은 여분의 공간. 사용자 데이터가 아니라 그 sector에 대한 lsn를 저장하는 용도

#### 3.1.2 Block mapping
* sector mapping은 RAM 요구량이 커서 소형 임베디드 시스템에 부적합 -> 이를 해결하기 위해 제안됨
* **logical block 내 sector offset = physical block 내 sector offset** => logical sector에 대한 정보로 이거에 대응되는 physical sector 정확히 알 수 있음(sector mapping과 달리 psn 필요X)
* logical block이 m개면 매핑 테이블 row 크기도 m

![블럭 매핑 예](/assets/img/posts/FTL_2/image-1.png)
* 가정: logical block 4개 -> 매핑 테이블 row 크기 4
* `write(9, A)`:
    * 두 개로 쪼갬
        * logical block number = 9/4 = 2 (몫). lsn이 몇 번째 logical block에 속하는지
        * logical sector offset = 9%4 = 1 (나머지). 그 logical block 안에서 몇 번째 sector인지
    * 매핑 테이블에서 logical block 2 -> physical block 1(매핑 테이블은 block단위로만 매핑 정보를 가지고 있음)
    * physical sector offset = logical sector offset이므로 물리 위치를 바로 결정 가능

* 장점: sector mapping 대비 매핑 정보량이 훨씬 작음(logical sector에 대한 정보로 이거에 대응되는 physical sector 정확히 알 수 있으니까)
* 단점: empty sector 안 찾고 그냥 무조건 logical sector 정보에 대응되는 physical sector에 씀 => 
    if 같은 logical sector number로 반복해서 write 명령이 오면 
        -> 많은 copy/erase 연산 필요 => 성능 심각하게 저하
* 구현 시 power-off recovery를 위해 block-level(logical block <-> physical block 대응) 매핑 정보를 flash memory에 저장해야 함
    * (lbn, pbn)쌍들의 전체 테이블 저장

#### 3.1.3 Hybrid mapping
* sector mapping과 block mapping 각각의 단점을 보완하기 위해 도입됨
* 이름 그대로 
    1) block mapping 기법으로 해당 physical block을 먼저 찾고
    2) 그 physical block 내에서는 sector mapping 기법으로 비어있는 sector를 찾음

![Fig. 4 하이브리드 매핑 예시](/assets/img/posts/FTL_2/image-2.png)

* `write(9, A)`:
    * logical block number = 9/4 = 2 -> 매핑 테이블에서 physical block 1을 찾음(lbn = 2에 매핑되는 pbn = 1이니까)
    * physical block 1 획득 후, FTL이 update하기 위해 empty sector를 할당
    * 예시에서 physical block 1의 첫 번째 sector가 비어있으므로 -> 첫 sector 위치에 데이터를 씀
    * 이때 logical offset(9%4=1)과 physical offset(0)이 서로 다름(그냥 빈 데에 넣었으니까) -> **logical sector number(9)를 physical block 1의 page 0 spare area에 기록**해야 함
    * 매핑 테이블 재구성 시 logical sector number뿐 아니라 각 physical block의 spare area에 기록된 logical block number도 필요

* **Read 동작**:
    1. lsn으로 매핑 테이블에서 physical block number를 찾음
    2. 해당 physical block의 spare area들에서 logical sector number를 읽어서, 요청된 데이터의 가장 최근 값(most recent value)을 얻음
    (lsn -> lbn 계산 -> 매핑 테이블 조회로 pbn 찾음
        -> 그렇게 찾은 블럭 안 모든 spare area를 읽으면서 내가 찾는 lsn과 같은지 확인하고 여러 번 나오면 최근에 쓰인 걸로.) 

#### 3.1.4 Comparison
* FTL 알고리즘 성능은 (1) file system이 요청하는 read/write 성능, (2) 매핑 정보 저장을 위한 memory 요구량 두 가지 기준으로 비교
* 비교 전제: 매핑 테이블은 RAM에 유지되고, 매핑 테이블 access 비용은 0이라고 가정
* read/write 성능은 flash I/O 연산(read, write, erase) 횟수로 측정

**비용 공식**
$$C_{read} = xT_r \quad (1)$$
$$C_{write} = p_iT_w + p_o(xT_r + T_w) + p_e(T_e + T_w + T_c) \quad (2)$$

* $C_{read}, C_{write}$: file system 계층에서 요청한 read/write 명령의 비용
* $T_r, T_w, T_e$: flash memory 계층에서 처리되는 read/write/erase 명령의 비용
* x: read 연산 횟수

**Read 비용 (식 1)의 변수 x**
* sector mapping, block mapping: **x = 1** -> 매핑 테이블에서 읽을 sector를 바로 결정 가능
* hybrid mapping: **1 <= x <= n** (n = block 내 sector 개수) -> physical block의 spare area에 저장된 logical sector number를 스캔해야 요청 데이터를 읽을 수 있음
    * -> hybrid mapping이 sector/block mapping 대비 read 비용이 더 높음

Write 비용 (식 2)의 경우3 -> 무조건 이 셋 중 하나
1. **$p_i$**: write 요청이 in-place 위치에서 직접 수행될 확률
    * 매핑 테이블이 가리키는 physical position(sector mapping이면 sector, block mapping이면 block, hybrid도 block)이 비어있어서 그냥 그 자리에 바로 씀
2. **$p_o$**: block 내 empty position을 스캔한 후에 write가 수행될 확률
    * 매핑 테이블이 가리키는 physical position에 이미 데이터가 있어서 빈 자리를 찾아서 다른 데에 씀 -> 추가 read 연산 필요할 수도 있음
3. **$p_e$**: write 연산이 erase 연산을 수반할 확률
    * 빈 자리가 없어서 victim block을 하나 지워서 확보해야 하는 경우 -> ? 질문
    * erase가 필요한 경우 FTL 동작 순서:
        1. erase 대상 block의 valid data를 free block으로 copy ($T_c$)
        2. write 연산 수행 ($T_w$)
        3. 매핑 테이블 갱신
        4. 원본(source) block erase ($T_e$)
* $T_e, T_c$는 $T_r, T_w$ 대비 고비용 연산 -> **$p_e$가 write 비용의 핵심 변수**
(p_e가 erase, copy를 요구하기 때문에)

* **sector mapping**: write당 erase 발생 확률이 상대적으로 낮음
* **block mapping**: write당 erase 발생 확률이 상대적으로 높음

**메모리(RAM) 요구량 비교**
![Fig. 5 RAM 요구량](/assets/img/posts/FTL_2/image-3.png)

* 가정: flash memory 용량 128MB(8192 block) / 8GB(524288 block), 1 block = 32 sector
* addressing에 필요한 byte 수:
    * sector mapping: 128MB/8GB 모두 **3B** (모든 sector number 표현 필요)
    * block mapping: 128MB **2B**, 8GB **3B** (block number만 표현하면 됨)
    * hybrid mapping: 128MB **(2+1)B**, 8GB **(3+1)B** (block mapping용 byte + block 내 sector mapping용 1byte)
* 총 메모리 요구량:

| 구분 | 128MB | 8GB |
|---|---|---|
| Sector mapping | 3B×8192×32 = 768KB | 3B×524288×32 = **48MB** |
| Block mapping | 2B×8192 = **16KB** | 3B×524288 = 1536KB |
| Hybrid mapping | 2B×8192+1B×32×8192 = 272KB | 3B×524288+1B×32×524288 = 17920KB |

* **결론**: block < hybrid < sector 순서로 메모리 요구
    * block: 
        * block 단위로만 매핑 정보를 저장하면 됨
        * block 개수 자체가 sector 개수보다 훨씬 작음(1block에 32sector니까)
    * sector:
        * sector 단위로 정보 매핑 정보 저장
    * hybrid:
        * block 정보(누가 어느 block인지) + 그 block 안에서 sector 위치(1byte) 둘 다 필요
        * 근데 sector가 32개니까 block 8192개 각각에 대해 2byte(block 정보) + 1byte×32(그 block 안의 32개 sector 각각의 위치 정보) -> 272KB

### 요약 정리
| | Sector mapping | Block mapping | Hybrid mapping |
|---|---|---|---|
| 매핑 단위 | sector 1:1 | block 1:1 (offset 고정) | block 매핑 + block 내부는 sector처럼 자유롭게 |
| RAM 요구량 | 가장 큼 | 가장 작음 | 중간 |
| Read 비용 | 낮음 (x=1) | 낮음 (x=1) | 높음 (spare area 스캔 필요) |
| Write/erase 빈도 | erase 확률 낮음 | 같은 위치 반복 write 시 erase 확률 높음 | 절충 |

## 4. Case study

### 4.1 Mitsubishi

* **Mitsubishi 알고리즘**: 3.1.2절 **block mapping** 기반
* block mapping 기반으로 하는 이유: sector mapping의 한계 극복
    * sector mapping 한계:
    1. map table을 위한 대용량 저장 공간 필요
    2. 전원 넣을 때 map table construction 비용이 큼
* **1개의 logical block = 1개의 physical block** (1:1 block mapping)
    근데 block mapping 쓰면 같은 lsn에 여러번 write 하면 계속 erase해야 하는 문제가 있음
    => space sector 도입
* block mapping과의 차이점: **space sector**
    * physical block = general sector area + space sector area
    * logical block이 m개 sector로 구성되면, physical block은 m개 sector + 추가 n개의 space sector로 구성
    * **general sector area**: physical/logical sector offset이 동일 (block mapping 규칙 그대로)
    * **space sector area**: physical/logical sector offset이 동일할 필요 없음 (자유롭게 씀)

* 동작 예시
    ![Mitsubishi 동작 예시](/assets/img/posts/FTL_4/image.png)
    * 가정: 1 physical block = general sector 2개 + space sector 2개
    * `write(0, A)`:
        * lbn = 0/2 = 0, logical page offset = 0%2 = 0 계산
        * 매핑 테이블로 physical block number 9 획득
        * pbn=9의 physical page offset 0이 비어있으므로 -> 그 위치(general sector area)에 A를 씀
    * 추가 write(1,B), (2,C), (3,D) 등도 같은 방식으로 처리(다른 pbn으로)
    * `write(0, G)` (lsn 0에 대한 재write):
        * pbn=9의 physical page offset 0은 이미 점유됨(순수 block mapping이었다면 여기서 copy+erase 필요)
        * -> 대신 **첫 번째 space sector 영역**에 씀
        * 이때 logical sector number(0)를 spare area에 기록
    * **Read 동작**: logical sector number 0을 읽을 때, spare area들을 스캔해서 가장 최신 버전을 찾음

* Mapping table의 Reorganization 과정
    1. FTL이 free block을 하나 획득
    2. 원래 physical block의 valid sector들을 새 block으로 copy
    3. mapping table을 적절히 갱신
        * 구체적으로는 victim block(옛 pbn)을 가리키고 있던 lbn 행을 찾아서, 그 행의 pbn 값을 새로 획득한 free block 번호로 교체
    4. 원래 block의 sector들이 완전히 새 block으로 옮겨진 후, 원래 block을 erase하여 free block list로 반환
        * 이렇게 valid만 따로 빼는 이유는 앞에서 봤듯 flash가 block단위 erase만 가능하기 때문에 지우려면 이렇게 해야 함.
        * 이건 3절에서 봤듯 write 요청이 erase를 수반하는 경우에 발생함. (general area, space area 둘 다 다 차서 빈 자리가 없을 때)
    * **Mitsubishi 방식은 항상 최소 1개의 free block을 reorganization용으로 유지함**

* 매핑 정보 저장 방식
    * 3.2.1절 **map block method** 사용
        * map block이라는 별도의 공간을 두고
        * 매핑 정보(logical block number, physical block number쌍)는 최신 map block의 비어있는 sector 하나에 기록
    * block mapping 기반이라 mapping table 크기가 상대적으로 작음

### 4.2 M-systems

* M-systems는 **ANAND**, **FMAX** 두 알고리즘 제안 (둘 다 block mapping 기반)
* 두 알고리즘 구조가 유사하여, 논문에서는 FMAX만
* Mitsubishi와의 차이: 하나의 logical block이 **2개 이상의 physical block에 매핑 가능**
* **FMAX**: 하나의 logical block이 primary block과 replacement block 매핑 가능(둘 다 physical block)
    * **primary block**: logical sector offset = physical sector offset (동일. block mapping 방식으로)
    * **replacement block**: logical sector offset != physical sector offset일 수 있음 (자유롭게 씀)

* FMAX 동작 예시 (Fig. 10)
    ![Fig. 10](/assets/img/posts/FTL_4/image-2.png)
    * 가정: 1 physical block = 4 sector
    * `write(4, A)`:
        * lbn = 4/4 = 1, logical page offset = 4%4 = 0 계산
        * 매핑 테이블로 physical block number 10 획득
        * pbn=10의 physical page offset 0이 비어있음(초기 상태) -> 그 위치(primary block)에 A를 씀
    * 추가 write(5,B), (6,C), (7,D) 등도 같은 방식(pbn=10에 순서대로 씀)
    * `write(8, G)`:
        * lbn=2 -> 매핑 테이블상 pbn=12, offset 0. 
        * pbn=12는 이미 점유됨(이미 'E'쓰임) -> **두 번째 physical block(pbn=9, replacement block)에 씀**
        * 만약 replacement block에도 빈 sector가 없으면 -> copy와 erase 연산 수행
    +++) 그림에서 G가 아니라 H 밑에만 8이 있는 이유는 G보다 H가 나중에 쓰인 거라 거기에만 lsn을 써주는 거임 -> ?
    * 매핑 정보 저장 방식
        * per-block method 사용
            * 각 physical block마다 자기에게 해당하는 lbn 저장
        * FMAX는 RAM table로 "logical block -> physical block 2개(primary+replacement)" 매핑을 관리
        * -> 1:1 block mapping보다 더 많은 RAM 크기가 필요함(당연한 게 block 두 개에 대한 정보를 저장함)

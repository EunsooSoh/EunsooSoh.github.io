1. 트랜잭션
    
    : 하나의 작업을 수행하기 위해 필요한 데이터베이스 연산들을 모아놓은 것
    
    - 논리적 작업의 단위
    - DB 회복, 병행제어의 기본 단위
    - 특성 4가지: ACID
        
        —회복기능이 필요로 하는 것—
        
        (1) 원자성: 연산이 모두 정상적으로 수행되거나 아예 수행되지 않아야 함
        
        (4) 지속성: 트랜잭션이 수행 완료되면 DB에 반영된 결과가 영구적으로 보존되어야 함
        
        —병행제어기능이 필요로 하는 것—
        
        (2) 일관성: 트랜잭션 수행 이후에 DB가 모순 없이 일관성 있는 상태여야 함
        
        (3) 격리성: 수행 중인 트랜잭션이 완료될 때까지 다른 트랜잭션이 중간 연산 결과에 접근할 수 없어야 함
        
    - 연산 2가지
        - commit: 작업 완료 선언. 결과를 DB에 반영
        - rollback: 작업 실패에 따른 취소 선언
    - 상태 5가지
        
        (1) 활동: 트랜잭션 수행 시작해서 현재 수행 중
        
        (2) 부분 완료: 마지막 연산 실행까지 수행함
        
        (3) 실패: 장애가 발생해 수행 중단
        
        (4) 완료: commit 연산까지 함
        
        (5) 철회: 수행 실패로 rollback함
        
        —트랜잭션 종료—
        

1. 장애와 회복
    - ~~장애3: 시스템이 제대로 동작하지 않는 상태~~
        
        ~~(1) 트랜잭션 장애: 오류로 인해 발생~~
        
        ~~(2) 시스템 장애: 하드웨어 결함에 의해~~
        
        ~~(3) 미디어 장애: 디스크 훼손에 의해~~
        
        → DB 저장 장치 3가지
        
        - 휘발성 저장장치: 장애 → 데이터 손실
        - 비휘발성 저장장치: 장애나도 데이터 손실은 안 됨. 저장 장치에 이상이 생기면 데이터 손실될 수도 있음
        - 안정 저장장치: 비휘발성에 복사본 여러 개 저장해서 영구적으로 저장함
        - 메모리와의 관계
            
            <변수> ————— <버퍼 블록> ————— <디스크>
            
            A → write(A) → output(A)
            
            반대는 read(B), input(B)
            
    - 회복: 회복 관리자가 장애 발생 시 DB를 장애 발생 전 일관된 상태로 복구하는 것
        
        (데이터 중복)을 이용함
        
        (1) 로그: DB에서 변경 연산 실행될 때마다 변경 이전 값, 이후 값을 별도 파일에 기록
        
        (2) 덤프: 주기적으로 DB 전체를 복사하는 것
        
        - 연산 2가지
            - redo: 변경 연산 재실행
            - undo: 변경 연산 취소
        - 회복 기법
            
            (1) 로그 회복 기법
            
            1. 즉시 갱신 회복 기법
                
                : 트랜잭션 수행 도중에 데이터 변경 연산 결과를 DB에 즉시 반영 ⇒ undo: commit 이전에 장애 그냥 취소, redo: commit 이후에 장애난 것에 대해서
                
            2. 지연 갱신 회복 기법
                
                : 트랜잭션 부분 완료 전까지 로그에 기록했다가 완료 후에 DB에 반영 ⇒ redo: commit 이후에 장애난 것에 대해서
                
                ++ commit 이전에 그러면 undo 할 게 없음
                
            
            (2) 검사 시점 회복 기법: checkpoint를 활용해서 가장 최근 checkpoint 이후부터 회복
            
            - commit 안 된 거 다 undo
            - commit 된 거
                - checkpoint 이전에 commit: 아무것도 하지 않음
                - checkpoint 이후에 commit: redo
            
            (3) 미디어 회복 기법: 덤프 이용
            
2. 병행제어 = 동시성 제어
    
    : 병행 수행할 때 발생하는 문제들 예방하기 위한 것
    
    병행 수행: 트랜잭션 여러 개를 동시에 인터리빙 방식으로 진행하는 것
    
    - 문제
        
        (1) 갱신 분실: 하나의 트랜잭션 결과를 다른 트랜잭션이 덮어써서 결과 무효
        
        (2) 모순성: 여러 데이터 변경 시 일관성 없는 상태의 데이터로 연산해서 잘못된 결과가 생기는 문제
        
        (3) 연쇄 복귀: 장애 발생 시 변경된 데이터를 가져간 다른 트랜잭션도 연쇄적으로 취소해야 하는데 이미 완료되어서 rollback할 수 없는 문제
        
    - 트랜잭션 스케줄
        
        (1) 직렬 스케줄: 인터리빙 방식 아님, 결과는 정확함을 보장하지만 병행수행은 아님
        
        (2) 비직렬 스케줄: 인터리빙 방식으로 병행 수행. 결과가 정확함을 보장하지 않음
        
        (3) 직렬 가능 스케줄: 비직렬 스케줄이지만 직렬 스케줄과 동일한 결과를 얻음
        
        (직렬 가능성): 수행결과가 동일한 직렬 스케줄이 있음
        
    - 로킹
        
        : 동일 데이터에 동시 접근하지 못하도록 상호 배제
        
        - lock: 독점권 요청
            - 공용 lock: 여러 트랜잭션이 실행 가능. 읽기만 가능
            - 전용 lock: 하나만 가능. 읽기, 쓰기 가능
        - unlock: 독점권 반환
        - 로킹 단위(로킹 연산 대상 데이터 크기) 커짐 → 병행성 감소, 제어 용이성 증가
        - 2단계 로킹 규약(2PLP)
            
            : lock, unlock을 단계 나눠서 실행
            
            (1) 확장 단계: lock만 할 수 있음
            
            (2) 축소 단계: unlock만 할 수 있음
            
            시나리오: 트랜잭션 처음 수행 → (확장단계) → (unlock) → 축소단계 
            
            ⇒ 첫 번째 unlock 전 모든 lock을 실행해야 함
            
        - 교착 상태: 서로 상대가 독점하고 있는 데이터가 unlock되기를 기다리며 수행 중단한 상태

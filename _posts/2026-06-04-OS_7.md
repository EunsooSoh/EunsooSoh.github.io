### 1. 주소 바인딩과 동적 링킹 (Address Binding & Dynamic Linking)

CPU가 실행하는 논리적 주소가 실제 물리적 메모리 주소로 언제 확정되는지

1. **Compile Time**: 컴파일 시점에 물리 주소가 확정. 위치가 바뀌면 재컴파일이 필요하여 현대에는 쓰이지X.
2. **Load Time**: 프로그램이 메모리에 적재될 때 주소가 배정되며, 실행 중간에 위치를 바꿀 수X.
3. **Execution Time (자유 이동)**: **현대 OS의 표준 방식**으로, 실행 중에도 프로세스가 메모리 내 위치를 옮길 수 있음. 이를 위해서는 매 메모리 접근마다 변환을 돕는 MMU(하드웨어)가 필수적.
    - MMU는 논리주소를 물리주소로 변환해줌. relocation regs, limit regs를 확인해서 한 프로세스가 다른 프로세스나 OS의 영역을 침범하지 못하게 함
- **동적 링킹 (Dynamic Linking)**: 외부 라이브러리를 실행 파일에 포함하지 않고, 실행 중 처음 호출될 때 연결. 여러 프로세스가 하나의 공유 라이브러리를 RAM에 한 번만 적재해 돌려씀. 외부함수 호출 시 **PLT를 거침. 처음 호출할 때만 실제 함수의 주소를 찾아 GOT에 저장 (지연 바인딩)**. ⇒ 프로그램 시작 시간 단축
    - cf. dynamic loading: 프로그램 내 내부 모듈을 첫 호출 시 로드
        
         ⇒ 호출 안 하면 그냥 RAM 사용 X
        
        - 로드한 건 프로세스 하나에서만 사용
    
    +.. 한 줄 요약: 동적 링킹은 외부라이브러리를 호출될 때 링킹, 동적 로딩은 처음 호출될 때 메모리에 로드
    
    - **1. 개념 정의**
        - **PLT (Procedure Linkage Table)**: 외부 라이브러리 함수를 호출할 때 직접 호출하는 대신 거쳐 가는 '고정된 입구' 역할의 작은 중계 코드(stub)들의 모음.
        - **GOT (Global Offset Table)**: 외부 함수의 **'실제 메모리 주소'가 보관되는 테이블**.
    - **2. 구체적 동작 원리 (지연 바인딩, Lazy Binding)**
        
        프로그램 내에서 호출 코드는 외부 함수의 실제 주소를 몰라도 무조건 **PLT라는 고정 입구**를 향해 호출(**`callq`**)을 보냄.
        
        1. 프로그램이 외부 함수를 호출하면, 먼저 해당 함수의 PLT stub 코드로 진입.
        2. PLT 코드는 GOT 테이블의 특정 엔트리에 적힌 주소로 점프(**`jmpq`**)하라는 명령을 내림.
        3. GOT에 적힌 실제 주소를 통해 **곧바로 함수가 실행**
            1. 하지만 첫 호출에는 GOT에는 아직 실제 함수의 주소가 없으니까 동적 링커는 해당 외부 함수 **실제 주소를 찾아내서 GOT 테이블에 채워 넣고,** 해당 함수로 점프하여 실행을 마침.
            2. 다음부터는 그냥 GOT에 적힌 주소로 바로 점프.

### 2. MMU와 메모리 보호

MMU는 CPU가 사용하는 논리주소를 물리주소로 변환하는 하드웨어

- **Logical vs Physical 분리**: CPU는 0번지부터 시작하는 연속된 논리 주소(Logical Address)를 보고, 실제 RAM은 분산된 물리 주소(Physical Address)를 가짐.

![프로세스가 보는 logical address space: 낮은 주소(0x0000)부터 code/data/heap/free virtual area/stack 순서로 배치된 연속적인 구조](/assets/img/posts/OS_7/image-4.png){: width="700" height="464" }

![RAM의 빈 공간에 프로세스들(P1, P2)이 순서 없이 입주해 물리 주소가 제각각으로 배치되는 예시](/assets/img/posts/OS_7/image-5.png){: width="700" height="460" }

- **보호와 변환 원리**: 초기 모델에서는 MMU 내부의 **Relocation(Base) 레지스터**가 물리적 시작 주소를 더해주고, **Limit 레지스터**가 프로세스의 크기를 넘는 불법 접근을 차단하여(Trap 발생) 메모리를 보호했음. 이 변환과 검사는 하드웨어를 통해 단 한 번의 명령어 사이클 내에 처리.

### 3. 메모리 할당과 단편화 (Allocation & Fragmentation)

물리 메모리를 프로세스에게 분배하는 방식

![메모리 할당 방식 분류: 연속 메모리 할당(고정 크기/가변 크기)과 분할 메모리 할당(Segmentation/Paging)](/assets/img/posts/OS_7/image-7.png){: width="700" height="236" }

- **연속 할당 (Contiguous Allocation)**: **프로세스를** 통째로 넣는 방식.
    - 고정 크기
        - 메모리를 미리 고정 크기 파티션으로 분할
        - 1파티션 - 1프로세스
        - 프로세스 < 파티션 → 내부 단편화: 할당된 메모리 구역 안에 사용되지 않고 남는 빈 공간이 생기는 현상(할당된 파티션 내부가 낭비)
    - 가변 크기
        - 프로세스 크기만큼 파티션 할당
        - 프로세스 종료 후 외부 단편화
        - 빈 공간(Hole)을 찾는 알고리즘으로(연속, 가변에 있음)
            - First-fit(첫 번째 큰 빈칸) → 빈 공간 순서대로 검색하다가 load할 수 있는 첫 번째
                - Searching overhead X → 빠름
            - Best-fit(가장 딱 맞는 빈칸) → 통으로 넣을 수 있는 것 중에 가장 작은 것
                - 남는 hole 이 작아짐
            - Worst-fit(가장 큰 빈칸) → 넣었을 때 빈공간 가장 많이 남음
        - **외부 단편화 (External Fragmentation)**: 남은 총 빈 공간은 충분하지만, 흩어져 있어 큰 프로세스를 수용X.
            
            ⇒ Compaction(압축) 작업은 하는 동안 시스템 정지시켜야 해서 실시간 시스템에 부적합. 심지어 메모리 대량 복사.
            
            ⇒ 프로세스를 불연속적으로 흩뿌려 배치하는 페이징(Paging)이 도입됨
            
- **분할 할당**
    - Segmentation:
        - segment 크기 가변
        - 코드, 데이터, 스택 같은 논리적 단위로 분할
        - 외부 단편화
    - Paging
        - Page 크기 고정(보통 4KB)
        - 마지막 페이지 내부 단편화

### 4. 페이징 (Paging)

**메모리를** 고정 크기 frame으로 분할

- 고정 크기 단위
    - 물리 메모리는 **Frame(DRAM에서 쓰는 단위)**
    - 논리 메모리는 **Page(CPU에서 쓰는 단위)**
    
    ⇒ 동일한 고정 크기(일반적으로 4KB) 조각으로 나뉨.
    
- **내부 단편화 발생**: 외부 단편화는 X, 프로세스 크기가 페이지 크기의 배수가 아닐 경우 마지막 페이지에 빈 공간이 남는 내부 단편화는 O (평균 1/2 페이지 크기 낭비).
- **Page Table**:
    - 각 프로세스마다 존재
        - 논리 주소의 Page 번호를 물리 주소의 Frame 번호로 변환해 주는 매핑 표.
        - 논리적으로는 연속된 페이지가 물리적으로는 분산된 메모리에 할당될 수 있음.
        - offset은 그대로 두고 page number만 frame number로 변환
            
            ![Logical Address의 Page 번호(p)로 Page Table을 인덱싱해 frame number(f)를 얻고, offset(d)은 그대로 전달해 Physical Address(f+d)를 구성하는 과정](/assets/img/posts/OS_7/image-8.png){: width="700" height="275" }
            
        - OS가 free frame list 가지고 있다가 할당해줌. N page짜리 프로세스 실행할 때 N frame에 할당해줌.
    - 메모리에 존재
        - 매번 '**페이지 테이블 접근**'과 거기서 얻은 frame number를 통한 '**실제 데이터 접근**' ⇒ 이렇게 메모리 여러 번 접근해서 도입한 게 TLB
        - PTBR (Page-Table Base Reg): 테이블 시작 주소
        - PTLR (Page-Table Length Reg): 테이블 크기
    - PTE(page table entry): page table 의 한 행
        - 개수는 총 페이지 수와 같음(2^page number bit 수)
        - single level일 때, PT 크기: PTE 수 * PTE 하나 크기
- 문풀
    - 단위 (1KB = 2^10bytes, 1MB = 2^10KB, …)
    - Page size가 offset bit를 정하고, 전체 주소 bit에서 offset bit 수 빼면 page number bit

### 5. TLB와 실효 접근 시간 (TLB & EAT)

- **TLB (Translation Look-aside Buffer)**: CPU 내부의 초고속 주소 변환 캐시(하드웨어). 특수한 경우를 제외하고는 TLB miss가 났을 때 변환한 Page-to-Frame 정보를 저장.
    - CPU가 page number를 TLB에 보내고,
        - TLB hit: 즉시 frame number 할당 → 메모리 한 번 접근
        - TLB miss: 페이지 테이블 조회 후 TLB에 추가 → 메모리 N(주소 level) + 1번 접근
- **EAT (Effective Access Time)**: TLB 적중률(Hit ratio)이 성능 결정.
    
    $$
    EAT= p· 10 + (1− p)· 20 = 20− 10p [ns]
    $$
    
    - 메모리 접근이 10ns라고 하면 위와 같이 됨. 근데 이건 예시이고 그냥 시험에 주어지는 대로.
    - p: TLB hit 확률 ⇒ 이 확률이 올라가면 EAT는 감소(당연함. 메모리까지 안 가도 될 확률이 올라가니까 시간도 더 적게 걸림)
- **성능 최적화**:
    - Context Switch마다 TLB를 비우는(Flush) 비용을 줄이기 위해 TLB entry에 **ASID/PCID: PID 태그**를 함께 저장 → 여러 변환 정보가 하나의 TLB에 공존할 수 있음. (context switch 발생하면 기존 TLB 아예 날렸음)
    - 멀티코어 환경에서 페이지 테이블 변경 → **TLB Shootdown 필요(**다른 코어의 TLB의 해당 부분 삭제: invlpg로)을 위한 IPI 통신 오버헤드가 발생.
        - 안 하면 과거의 권한 기록이 남아서 권한이 없는 페이지에 쓰기 작업을 해 일관성이 깨질 수 있음
    - **TLB Reach**: TLB가 miss 없이 다룰 수 있는 메모리 총량.
        - 크기: TLB entry 수 * page size
        - 늘리기 위해 DB나 VM 등에서는 2MB, 1GB 크기의 **Huge Page**를 적극적으로 사용. → hit ratio 증가

### 6. 거대 페이지 테이블 문제와 구조적 해법

64-bit(실제 48-bit 사용) 체계에서 4KB 페이지를 쓰면 1단계 페이지 테이블 크기만 프로세스당 **512GB**에 달하는 심각한 문제가 발생.

 ⇒ 해법

- **Multi-level Paging (계층적 페이징)**: 페이지 테이블 자체를 페이징하여 목차 형태로 사용하는 페이징 기법.
    - **사용하지 않는 빈 주소 공간(NULL - ex. stack과 heap사이)에 대해서는 inner table을 아예 생성X →** 페이지 테이블 크기를 줄여 메모리를 극적으로 절약.
    - TLB 관련
        - TLB hit: 즉시 frame number 할당 → 메모리 한 번 접근
        - TLB miss: 페이지 테이블 조회 후 TLB에 추가 → 메모리 **N(paging level) + 1**번 접근
            - 이 N이 table walk수
    - x86-64 아키텍처는 이를 4단계(또는 5단계)로 쪼개어 사용.
- **Hashed Page Table**: 주소 공간이 듬성듬성할 때 해시 알고리즘을 이용해 사용중인 page만 hash table에 보관. hash함수 잘 되어 있으면 search → O(1)
- **Inverted Page Table**: 프로세스별로 테이블을 두는 대신, 시스템 전체에 물리 프레임 개수만큼 PTE를 갖는 딱 1개의 테이블만.

### 7. 메모리 보호 비트 및  공유(Shared Pages & COW)

각 PTE 안에 들어가는 여러 비트들

- **Protection Bits(R/W/X)**:
    - **NX (No-Execute) 비트**: **데이터나 스택 영역의 코드**가 실행되는 것을 하드웨어적으로 막아 버퍼 오버플로우 공격을 방어.
        - **W^X**권한 강제(둘 다 1이 될 수 없음) ⇒ 주입한 걸 실행할 수 없음. (주입하면 실행을 못하든지, 실행하는 건 주입을 못함)
- **Valid/Invalid 비트**:
    - v: 접근이 합법적 and 현재 메모리에 적재되어 있음
    - i: 접근이 불법→SIGSEGV, 현재 메모리에 적재되어 있지X(=disk에)→swap in
- **reference bit**: 접근 기록
- **dirty bit**: 수정 기록
- **공유 페이지 (Shared Pages)**: 읽기 전용 코드(예: `libc.so`)는 여러 프로세스의 페이지 테이블이 동일한 물리 프레임을 가리키게.

### 8. 스와핑 (Swapping)

- **Swapping**: 물리 RAM이 부족할 때 프로세스를 디스크(Backing Store)로 내보내거나 들여오는 기법입니다. 전통적으로는 프로세스를 통째로 옮겼으나 비용이 너무 커서, 현대 OS는 페이지 단위로 쪼개어 스왑(Page-out / Page-in).

### 1. 가상 메모리의 본질 (Virtual Memory Core Concepts)

물리 메모리 크기에 제약받지 않고 거대한 주소 공간을 제공하는 것

- 사용자의 논리적 주소 공간과 실제 물리적 메모리를 분리
- 실행에 당장 필요한 페이지만 RAM에, 나머지는 디스크(Backing Store)에.
    - **Locality of Reference** 때문에 더 효율 좋아짐.
    - 힙이랑 스택 사이 빈 공간은 실제 프레임에 매핑되지 않아 메모리를 소모X

++ 추가: 가상 주소 공간의 0번지는 보통 비워두고, 시작 주소들은 보안 때문에 실행마다 달라질 수 있음

### 2. Demand Paging & Page Fault

Demand Paging:"페이지가 실제로 필요해질 때만 디스크에서 메모리로 적재"하는 기법. → 시작이 빨라짐.

- cf. swap in: 프로세스 전체를 메모리에
- **Valid/Invalid 비트의 확장**:
    - **'v' (Valid)**: 해당 페이지가 현재 물리 메모리에 적재되어 있음.
    - **'i' (Invalid)**: 해당 페이지가 물리 메모리에 없음. MMU가 발견하면 **Page Fault Trap**을 ****발생시킴. 이는 다음 두 가지 상황으로 나뉨:
        - 합법적 ****부재 **(Demand-load** 트리거로 ****작동**)**: 아직 한 번도 참조되지 않아 메모리에 안 올라왔거나, 메모리가 부족해 디스크로 쫓겨난 상태. -> 디스크에서 찾아 적재함.
        - 불법적 ****접근 **(**강제 ****종료**)**: 프로세스에 할당된 가상 주소 공간을 벗어난 잘못된 메모리 주소인 경우 \|\| 접근 권한 위반→ 운영체제가 프로세스를 Abort 시킴.
- Page fault있을 때만 적재

Page Fault: RAM에 적재되어 있지 않은 페이지에 접근하려고 할 때 발생하는 Trap

- **Page Fault 처리 과정**:
    
    ![Page Fault 처리 6단계: CPU가 참조 → trap 발생 → OS가 backing store에서 페이지 확인 → free frame에 missing page 적재 → page table 갱신 → 명령어 재시작](/assets/img/posts/OS_8/image-1.png){: width="700" height="593" }
    
    1. CPU가 페이지를 참조(logical 주소 참조)
    2. MMU가 Invalid 비트를 확인하고 Page Fault (Trap)를 발생 (→ 이때 원래 프로세스는 waiting 상태가 됨)
    3. OS가 합법 참조인지 확인하고, 디스크에서 해당 페이지의 위치를 찾음
    4. free frame 확보(없으면 replace → 만약 쫓아냈으면 해당 page invalid로 변경) & RAM의 빈 프레임으로 가져옴
    5. 페이지 테이블을 갱신(새로 할당한 frame 번호로 매핑+그 페이지 Valid 설정)
    6. 중단되었던 명령어 재시작
    - 문제 상황
        
        : 메모리 쓰기보다 레지스터 증가가 먼저 처리된 상태에서 page fault가 발생하면, 명령어를 재시작할 때 잘못된 주소를 참조할 수 있음
        
        → (1) rollback (2) Pre-touch: 미리 fault 여부 확인
        
    - 메모리 정렬
        
        안 하면 만약 page fault 났을 때 어디부터 다시 실행해야 하는지 어려워짐. 그리고 한 변수가 일부만 fault 나기 전 페이지에 걸쳐서 거기만 이미 변경되었을 수도 있음 (=page fault 처리, restart 처리가 복잡해짐)
        
        - 자료형 크기
            
            
            | 자료형 | 크기 (Byte) | 시작 기준 (주소의 배수) | 비고 |
            | --- | --- | --- | --- |
            | char | 1 | 1의 배수 |  |
            | short | 2 | 2의 배수 |  |
            | int | 4 | 4의 배수 |  |
            | float | 4 | 4의 배수 |  |
            | long long | 8 | 8의 배수 |  |
            | double | 8 | 8의 배수 |  |
            | long | 4 또는 8 | 4 또는 8의 배수 | Windows(64bit)는 4바이트, Linux/Mac은 8바이트 |
            | 포인터 (int*, void* 등) | 8 | 8의 배수 | 32비트 환경에서는 4바이트 |
- **EAT (실효 접근 시간)**: 디스크 I/O가 동반되는 **Major Page Fault**의 비용은 메모리 접근 대비 만 배 이상(수 ms 단위) 비쌈.
    - 그 외 fault 종류(microsec 단위)
        - minor fault: 페이지가 이미 RAM에 있는데 PTE 설정 X
        - CoW fault: shared page에 쓰기 시도
        - Demand-zero fault: anonymous(heap, stack) 메모리에 첫 접근

++) RAM 수면때문에 모바일에서는 디스크 Swap 안 함

++) 현실에서는 locality를 노려 주변 페이지까지 한 묶음으로 미리 가져옴

### 3. Copy-on-Write (COW)

`fork()` 호출 시 부모의 전체 메모리를 복사하는 걸 "쓰기 시점"까지 미룸.

- 원리:
    - 초기에는 자식이 페이지 테이블만 복사해서 부모와 동일한 물리 프레임을 **읽기 전용(Read-only)으로 공유**
    - 둘 중 하나가 쓰기를 시도하면 Protection Fault(Trap)가 발생 & OS는 **그 순간에 해당 페이지만**(수정한 딱 하나의 페이지)을 **새로운 프레임으로 복사**하고 쓰기 권한을 부여.
        
        ⇒ 자식이 곧바로 `exec()`를 호출하는 패턴에서 불필요한 복사를 완벽히 피할 수 있음.
        

### 4. 페이지 교체 알고리즘 (Page Replacement)

: 메모리에 free frame이 고갈되었을 때, 어떤 페이지를 디스크로 내쫓을지(Victim) 결정하는 알고리즘

- 만약 내쫓을 페이지가 적재 이후 수정되었다면(**Dirty bit=1**), 덮어쓰기 전에 디스크에 변경 사항 반영해야 함. → I/O 두 번(다시 디스크에 가서 쓰고, 디스크로부터 새로 읽어옴)
    - cf. 수정 안 되었음(dirty bit = 0: 그냥 그 위에 디스크로부터 읽어온 내용 덮어씀)
- **Reference string**: 프로세스가 접근한 page number의 시퀀스만 적어둔 것 → 이거 사용
- 알고리즘
    - **FIFO (First-In First-Out)**: 가장 먼저 들어온 페이지를 쫓아냄.
        - 단순
        - 들어온 지 오래 되었지만 자주 쓰는 건 페이지 내쫓을 수 있음
        - **Belady's Anomaly**가 발생할 수 있음
            
            : 프레임 수를 늘려도 오히려 Page Fault가 증가
            
    - **OPT (Optimal)**: 가장 나중에 쓰일 페이지를 쫓아냄.
        - 미래를 알 수 없어 실현 불가능.
    - **LRU (Least Recently Used)**: 가장 오랫동안 안 쓴 페이지를 쫓아냄.
        - OPT에 근접하며 Anomaly가 발생하지X (Stack property: 가장 최근에 쓴 게 늘 top에)
            - Bottom이 항상 victim
            - Page hit시 해당 page number를 top으로
        - 매번 메모리를 접근할 때마다 시간을 기록하거나 리스트를 갱신해야 하는 막대한 하드웨어 오버헤드가 발생 → 완벽한 구현은 불가능.
    - **Clock 알고리즘 (Second-Chance)**: LRU의 현실적인 근사 방식.
        - 하드웨어가 페이지 접근 시 **Reference bit를 1로 세팅(초기 0)**
        - OS가 시계바늘처럼 순회하며 비트가 1이면 0으로 깎음(최근에 쓰인 적 있으니까 한 번은 봐줌. 두 번째 걸림 = 한 바퀴 도는 동안 아무도 그 frame 안 찾음 → 쫓겨남)
        - **0인 페이지를 찾아 Victim**으로 선정
            - 최악: 다 1이어서 한 바퀴 다 돌고 나서야 처음 거를 victim으로.
            
            → enhanced second chance
            
            | Victim 우선 순위 | Ref | Dirty |
            | --- | --- | --- |
            | 1 | 0 | 0 |
            | 2 | 0 | 1(disk에 write back 필요) |
            | 3 | 1 | 0 |
            | 4 | 1 | 1 |
        - 디스크 I/O를 아끼기 위해 더러운(Dirty) 페이지보다는 깨끗한(Clean) 페이지를 우선 교체
    - **현대 OS의 최적화**:
        - **Two-List LRU**
            - Active/Inactive **List**
            - **메모리 압박 시 inactive에서만** clock 돌려서 victim 선택
        - **MGLRU**
            - 세대별로 구분
    - 추가 개념
        - File-backed page: 디스크에 원래 원본 파일이 존재하는 페이지. 재요청 시 그냥 다시 읽음
        - Anonymous page: 쫓아 내려면 swap space에 무조건 write back필요(heap, stack같은 것) → swap space가 빠르면 그냥 이것도 비율 높여서 많이 쫓아냄
        - Page-buffering: victim을 바로 디스크에 쓰지 않고 buffer에 보관해서 만약 필요해지면 디스크 I/O없이 즉시 재활용하고, 실제 write back은 디스크 I/O가 한가할 때
        - NUMA(Non Uniform Memmory Access): CPU마다 가까운 전용 메모리 슬롯을 따로 둠. 자기 메모리를 접근할 때는 빠르지만 다른 CPU의 메모리를 접근할 때는 느림.
            - 스레드를 실행 중인 CPU 근처 메모리에 frame할당
            - 스레드가 다른 CPU로 옮겨도 메모리를 따라 옮기진 않음
            - 대신 스케줄러가 스레드를 다시 가까운 CPU에 묶음

### 5. 프레임 할당과 스레싱 (Frame Allocation & Thrashing)

- **프레임 할당 (Frame Allocation)**
    - **할당 방식:** 프로세스마다 균등하게 할당하거나 크기에 비례하여 할당
    - **초기화:** 새 frame을 할당할 때는 반드시 0으로 채워서 넘김 (보안 및 일관성 유지 목적)
    - **Global Replacement:**
        - 빈 프레임을 찾을 때 시스템 전체를 뒤지는 방식
        - 장점: 시스템 전체의 처리량(Throughput) 면에서 유리
        - 단점: page fault가 자주 나는 프로세스가 남의 프레임을 뺏어서 Starvation 위험 존재
    - local replacement:
        - 자기 working set 못 늘리면 fault 폭증(다른 프로세스의 frame을 건드리지 않으니까)
- **워킹 셋과 스레싱 (Working Set & Thrashing)**
    - **Working Set:** 각 프로세스가 특정 시간에 집중적으로 참조하는 페이지의 집합
        - working set window $\Delta$
        - 워킹 셋 윈도우 크기를 늘리려면 히스토리 비트의 개수를 늘리거나 타이머 주기를 늘려야 함
        - WS(t) = {P_i가  $[t, t-\Delta]$에 참조한 페이지}
            - window가 너무 큼: 여러 locality 섞임
            - window가 너무 작음 → locality 다 커버하지 못함
        - \|WS\| = working set size
        - $D = \Sigma\|WS_i\|$
    - **스레싱 (Thrashing):**
        - 현상: 프로세스들이 명령어 실행보다 Page fault의 디스크 I/O 처리에 더 많은 시간을 쏟는 상태 (CPU 사용률 급감)
        - 원인: 프로세스에 할당된 frame이 locality(내가 지금 집중적으로 쓰는 page들)보다 작음 → 어떤 페이지를 쫓아내도 어차피 다시 필요해짐

**스레싱 방지 기법 (Working Set & PFF)**

- **Working Set Model:**
    - 모든 프로세스의 Working Set 총합($D$)이 물리 메모리($m$)를 초과하면 스레싱으로 간주 → 일부 프로세스를 통째로 Swap-out 시킴
    - history bits =[b_t-1, b_t-1] 최근 2주기의 reference bit
- **PFF (Page-Fault Frequency):** Page fault 비율의 상한/하한선을 설정하여 관리하는 기법
    - 상한선을 넘은 프로세스한테 프레임을 더 주고, 하한선 아래로 떨어지면 프레임을 회수

### 6. 커널 메모리 할당 (Kernel Memory Allocation)

- 커널 영역은 Page Fault를 스스로 처리할 수 없어 **디맨드 페이징이 불가능.**
- DMA를 위한 물리적 연속성이 요구.
- **Buddy System**: 물리 메모리를 2의 거듭제곱 크기로 가장 딱 맞게 계속 1/2로 쪼개어 할당 → 내부 단편화가 발생할 수 있음. 해제 시 짝꿍(Buddy) 블록이 비어있으면 빠르게 합쳐 큰 블록을 복구함. 이렇게 합치는 속도가 매우 빨라서 이걸 함. (이런 식으로 쪼갬)
    
    ![Buddy System이 32KB를 16KB씩 절반으로 쪼개고, 그 중 한 16KB 블록에서 12KB만 사용해 4KB 내부 단편화가 발생하는 예시](/assets/img/posts/OS_8/image-2.png){: width="700" height="254" }
    
- **Slab Allocator**: PCB와 같은 특정 커널 객체 타입마다 전용 캐시를 두고, 슬랩을 미리 해당 객체 크기로 조각내어 관리. 내부 단편화가 거의 없고 객체 재사용이 매우 빠름.
    - Slab: 연속된 페이지 묶음
    - Cache: 한 타입의 객체를 위한 슬랩들의 집합

### 7. 기타 중요 고려사항

- **프로그램 구조와 지역성**: 2차원 배열을 C언어(행 우선, Row-major → 같은 행은 같은 페이지에)에서 열 방향으로 순회하면 매 반복마다 새로운 페이지를 건드리게 되어 막대한 Page fault가 발생. **데이터의 물리적 구조와 접근 순서(배치)를 일치**시키는 것이 중요.

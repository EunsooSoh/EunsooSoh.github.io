1. 스케줄링 기본 가정, 평가 지표
    - 가정
        
        (1) 모든 작업은 실행 시간이 동일하다
        
        (2) 모든 작업은 동시에 도착한다
        
        (3) 작업은 시작되면 완료될 때까지 실행한다
        
        (4) 모든 작업은 CPU만을 사용한다
        
        (5) 작업의 실행 시간을 미리 알고 있다
        
    - 평가 지표
        - Batch 시스템: 한데 모아 제출하고 결과가 나올 때까지 기다림 
        → 반환 시간 중요
        - 대화형 시스템: 사용자가 명령을 내릴 때마다 즉각적 반응
        → 응답 시간 중요
2. 반환 시간 최적화
    - 선점: OS가 강제 중단 X(작업이 스스로 끝내거나 양보할 때까지 계속 실행)
    - 비선점: OS가 강제 중단시키고, 다른 작업에 CPU 넘길 수 있음
    
    (1) FIFO: 도착 순서대로 실행
    
    - first in first out
    - 비선점
    
    (-) convoy effect(호위 효과): 긴 작업 뒤 짧은 작업이 오랜 시간 대기
    
    (2) SJF: (1) 완화 → 짧은 것 먼저 실행
    
    - shortest job first
    - 비선점
    
    (-) 짧은 게 늦게 도착하면 교체 불가
    
    (3) STCF: (2) 완화 → 늦게 도착해도 (3) 완화 → 그게 더 짧으면 원래 하던 거 끊고 들어감
    새로운 작업 도착했을 때 현재 실행 중인 작업의 남은 실행 시간보다 실행 시간이 더 짧으면 교체
    
    - short time to completion first
    - 선점
3. 응답 시간 최적화
    
    (4) RR(Round Robin) 
    
    - 선점
    - 각 작업에 타임 슬라이스 q만큼 CPU 할당 → 반환
        - q가 커지면: FIFO와 동일 = 응답시간 붐따, 반환시간 붐업!!
        - q 작: 반대 근데, context switch 오버헤드 증가
    
    (5) I/O 반영: (4) 완화 → 작업이 I/O를 사용할 때 다른 작업 할당
    
4. 현실적인 스케줄링
    
    (6) MLFQ: (5) 완화 → CPU 사용 시간 추정
    
    - 과거 CPU burst 길이 바탕 다음 CPU burst 추정
    - 추정 공식
        
        아이디어: CPU 많이 씀 → 긴 작업 → 우선순위 낮게. 반대는 반대로
        
    - 규칙
        
        ① 우선 순위가 높은 것을 먼저 실행한다
        
        ② 우선 순위가 같으면 RR 방식으로 실행한다
        
        ③ 새로운 작업은 일단 최고 우선 순위 큐에 할당한다
        
        ④ - 타임 슬라이스 만료 이전에 CPU를 반납하면 우선 순위를 유지한다
        
        - Accounting: 누적 CPU 사용 시간을 모두 쓰면 우선 순위를 강등한다
        
        ⑤ priority boost: 일정 시간이 지나면 모든 작업을 최고 우선 순위 큐에 올린다 ⇒ 기아 방지
        
5. 공정성 중심
    
    (1) lottery 스케줄링(확률적 보장)
    
    ```c
    int winner = random() % total_tickets; // 당첨 번호
    int counter = 0;
    for (n=head;;n = n->next) {
    	counter += n->tickets; // 작업 번호표 범위의 끝
    	if (winner < counter) break; // winner가 이 번호표 안에 있음-> ?
    }
    run(n);
    ```
    
    각 프로세스에 티켓 부여 → 스케줄링할 때 무작위로 티켓을 뽑음 → 당첨된 프로세스가 CPU 사용
    
    - 확장 메커니즘
        - Currency: 그룹 내 지분 재분배
        - Transfer: 클라이언트가 서버에 티켓 양도
        - Inflation: 버스트 구간에서 자기 티켓 일시 증감
    
    (-) 티켓 배분을 어떻게 할지 결정하는 게 쉽지 않음, 확률 기반이라 장기적으로 티켓 비율에 수렴할 뿐, 단기적으로는 공정하지 않을 수 있음
    
    (2) stride 스케줄링(결정론적 보장)
    
    pass가 가장 작은 것을 실행
    
    공통 기준값 k에 대해서 stride = k/(ticket 수)결정하고, 
    실행할 때마다 pass += stride함
    
    ex. 리눅스 “vruntime”이라는 걸 pass로 씀
    
6. 멀티코어 스케줄링
    - 구조
    - 캐시 일관성(coherence) 문제: 한 코어에서 수정한 정보가 다른 코어에 반영되지 않은 것 (코어 1이 수정했는데 코어 2는 옛날 정보 가지고 있음)
        
        ⇒ 하드웨어 프로토콜로 처리
        
    - 캐시 친화성: 프로세스를 최근에 실행했던 코어에 계속 배치해야 L1, L2 캐시의 데이터 재사용 증가 → warm start 가능 → 성능up!
    
    (1) SQMS(Single Queue Multi processor Scheduling)
    
    - 모든 코어가 하나의 글로벌 큐 공유 
    → (-) lock 경합 발생(하나의 코어가 큐를 갱신하는 동안 나머지는 대기)
        
        (+) 구현이 단순, 
        자동 부하 분산 → (-) 코어를 넘나들어 캐시 친화성 떨어짐
        
    
    (2) MQMS(Multi Queue Multi processor Scheduling)
    
    - 모든 코어가 자신만의 독립된 큐를 가짐
    
    (-) 부하 불균형: 특정 코어의 큐만 비어 있을 수 있음 
    
    ⇒ Work Stealing: 잉여 코어가 바쁜 코어의 큐를 훔쳐보고 작업을 가져오는 것 → (-) 너무 잦으면 캐시 친화성 떨어지고, 너무 드물면 또 CPU 낭비임
    
    (+) 확장성, 캐시 친화성이 있음(자기만의 큐를 가지니까 자기가 했던 거 또 함)

### 1. 메모리 계층 구조와 결정론적 실시간성

* **속도-용량-비용의 트레이드오프:** 프로세서에 가까울수록 속도가 빠르지만 용량이 작고 비쌈
    * **PC vs MCU:**
        * 일반 PC: 캐시·DRAM·SSD 등 복잡한 다층 구조
        * MCU(Cortex-M4): DRAM/SSD 없이 <span class="hl-yellow">**온칩 Flash + SRAM**</span>

* **Cortex-M4에 범용 L1 캐시 및 MMU가 없는 이유:**
    * 캐시의 Hit/Miss 특성은 실행 시간의 비결정성 유발 → 최악 실행 시간 보장X
    * **SRAM:** SRAM/CCM은 항상 0 WS로 정속 접근 가능 → 실시간 응답 타이밍 예측 용이
        * **WS:** Wait State = Latency, 응답 수신까지 일정 사이클 동안 대기하는 것
    * 단, 느린 Flash 보완용으로 ART(2에 상술)를 추가함

* 데이터 저장 순서 (ex. 0x12345678)
    * 리틀 엔디언

    * 빅 엔디언

### 2. STM32 메모리 장치 특성 및 가속 기술

* **Flash 속도 한계와 ART Accelerator (ST의 기술):**
    * **문제:** STM32F407이 168MHz로 동작할 때, Flash의 읽기 속도 한계(~30MHz)로 인해 5 Wait States (대기 사이클)가 발생하여 CPU 체감 성능이 ~28MHz급으로 ↓

        ⇒ ART(Adaptive Real-Time Accelerator)

        * 코어 - Flash 접점에 위치
        * **128비트(16바이트) prefetch 버퍼 +** Instruction Cache를 통해 한 번에 4~8개 명령어를 미리 로드해 대기 시간을 0 WS에 가깝게
    * **특징:** 코어 관점에서는 투명하게 동작하며, 순차 실행 및 Cache Hit 시 성능 지연을 숨겨줌(분기 발생하면 점프한 데부터 새로 읽어야 함)

* <span class="hl-yellow">**메모리 정렬**</span>
    * **비정렬 접근:** 주소 경계를 걸치면 **2회 버스 전송 + CPU 데이터 조합** 과정이 필요해 2~3배 느려짐
    * 정렬 접근    
        * **정렬 원칙:** 32비트 데이터(`int`)는 4의 배수 주소에 배치해야 1회 버스 전송(1 cycle)으로 완결
            * 각 타입이 자기 크기 배수에 놓이게
                * char: 1의 배수(그냥 아무데나)
                * short: 2의 배수
                * int/float: 4의 배수 
                ++) 구조체 마지막은 다음 구조체 원소도 똑같이 정렬되게 패딩 필요
                
                → 근데 또 정렬할 때 패딩 써서 SRAM 낭비된다는 단점도 있음
                
            → **구조체 최적화:** 멤버 선언 시 큰 타입(`int` → `short` → `char`) 순서로 배치하면 패딩 ↓ → SRAM 절약

### 3. ARM Cortex-M 고정 메모리 맵 & MMIO

32비트 주소 공간(4GB)은 모든 Cortex-M 칩에서 공통 표준 영역으로 분할

| 영역 | 시작 주소 | 용도 | 주요 저장 대상 / 역할 |
|---|---|---|---|
| **A (Flash)** | `0x00000000` | Program Memory (0.5GB) | 코드(`.text`), 상수(`.rodata`) |
| **B (SRAM)** | `0x20000000` | Data Memory (0.5GB) | 변수(`.data`, `.bss`), 스택, 힙 |
| **C (Peripherals)** | **`0x40000000`** | Peripherals (0.5GB) | MMIO 제어 (GPIO, UART, ADC, Timer 등) |
| **F (PPB)** | `0xE0000000` | Private Peripheral Bus (0.5GB) | NVIC, SysTick, SCB 등 코어 내장 주변장치 |

* **0x0000_0000 에일리어싱 (Aliasing):**
    * CPU 리셋 시 항상 `0x0000_0000`에서 스택 포인터(MSP)와 Reset Handler 주소를 읽음
    * 하드웨어 핀(**BOOT0 핀**):
        * 설정에 따라 다른 데부터 실행
        * 기본값 0: 실제 Flash 주소(`0x0800_0000`)를 `0x0000_0000` 주소로 매핑 → 부팅 시 거기부터 읽음

* <span class="hl-yellow">**Memory-Mapped I/O (MMIO)**</span> **&** <span class="hl-yellow">**`volatile`**</span> **키워드:**
    1. **MMIO**: 주변장치의 레지스터를 일반 <span class="hl-yellow">**메모리 주소**</span>처럼 <span class="hl-yellow">**포인터**</span>로 읽고 쓰는 방식(`PERIPHERAL_BASE + OFFSET`)
        * 예제

            ```c
            // 주변장치(C 영역) 베이스 주소 및 오프셋 정의
            #define PERIPH_BASE 0x40000000U                       // Peripherals 시작 주소
            #define REG_OFFSET  0x14U                             // 특정 레지스터 오프셋 (예: ODR)

            // ① 주소 계산  ② 32비트 volatile 포인터로 캐스팅  ③ *로 그 주소에 접근 → 레지스터를 변수처럼 사용
            #define PERIPH_REG  (*(volatile uint32_t*)(PERIPH_BASE + REG_OFFSET))

            // 레지스터 비트 제어 (비트 연산)
            PERIPH_REG |= (1 << 0);   // 0번 비트 SET (HIGH 출력)
            PERIPH_REG &= ~(1 << 0);  // 0번 비트 RESET (LOW 출력)
            ```

        * GPIO 제어 및 BSRR 원자적 연산 코드
            * CMSIS 주변장치 헤더 방식에서는 주소를 직접 하드코딩하지 않고, **구조체 포인터(`GPIOB->MODER`, `GPIOB->BSRR`)** 형태로 MMIO를 제어

                ```c
                // 1. PB0 (mCube-M4 온보드 LED1) 핀을 출력 모드로 설정
                GPIOB->MODER &= ~(3 << 0);  // Clear
                GPIOB->MODER |= (1 << 0);   // General purpose output mode (01)

                // 2. BSRR 레지스터를 이용한 원자적(Atomic) LED ON/OFF
                GPIOB->BSRR = (1 << 0);     // Lower 16bit: Pin 0 SET (LED ON)
                GPIOB->BSRR = (1 << 16);    // Upper 16bit: Pin 0 RESET (LED OFF)
                ```

            * **CMSIS 헤더 매크로:** 주변장치 헤더 파일에는 이미 `#define __IO volatile` 매크로가 모든 레지스터 구조체에 적용되어 있음
            * **ODR 대신 BSRR을 쓰는 이유:** `ODR |= (1<<0)` 방식은 **Read-Modify-Write** 과정을 거침 → 연산 도중 인터럽트가 개입하면 다른 핀의 상태가 오염될 위험이 있음
            * **BSRR (Bit Set/Reset Register):** 원하는 비트에 `1`을 쓰기만 하면 하드웨어적으로 단 1 사이클에 원자적 SET/RESET 수행

    2. <span class="hl-yellow">volatile</span>
        * 써야 하는 상황
            * MMIO 주변장치 레지스터 접근 시
            * ISR(인터럽트)에서 수정하는 전역 변수
            * 멀티태스킹/RTOS 공유 변수

        * volatile 사용 전

            ```c
            #define SR (*(uint32_t*)0x40011000) // volatile 없음!

            // UART 전송 완료(TXE) 대기
            while (!(SR & (1 << 7)));           // 최적화 시 무한루프 발생!
            *(uint32_t*)0x40011004 = 'A';
            ```

            * 컴파일러는 `while` 루프 안에서 `SR` 주소의 값을 바꾸는 C 코드가 없으므로, 최적화(-O2) 시 한 번만 읽어 코어 레지스터(`R0`)에 캐싱해 두자고 판단

                ⇒ 하드웨어는 전송이 끝나 `0x40011000` 비트를 `1`로 바꿔놓았지만, CPU는 처음에 읽어둔 낡은 값(`0`)만 보며 무한 루프

        * volatile 사용 후

            ```c
            // volatile을 추가하여 매번 실제 메모리/하드웨어 레지스터 다시 읽기 강제
            #define SR (*(volatile uint32_t*)0x40011000U)
            #define DR (*(volatile uint32_t*)0x40011004U)

            while (!(SR & (1U << 7))) { } // 매 루프마다 실제 메모리 주소에서 LDR 수행
            DR = 'A';                      // 정상 전송 완료 후 탈출
            ```

            ⇒ **`volatile`** : 매번 실제 메모리/하드웨어 레지스터 접근을 강제(LDR 강제)
        * 생성 코드 비교
            * volatile X

                ```nasm
                    LDR R1, =0x40011000 
                    LDR R0, [R1] ; 루프 밖에서 한 번 읽고
                loop:
                    TST R0, #0x80 ; 캐싱된 값으로 계속 비교
                    BEQ loop
                ```

            * volatile O

                ```nasm
                    LDR R1, =0x40011000
                loop:
                    LDR R0, [R1] ; 루프 안에서 매번 읽음
                    TST R0, #0x80 
                    BEQ loop
                ```

### 4. RAM 분리 → SRAM, CCM (Core Coupled Memory)

* **CCM**
    * Core Coupled Memory
    * CPU D-Code 버스에 직접 연결 → 버스 매트릭스 경합 없이 CPU가 0 WS로 고속 접근

* **배치 가이드 (CCM vs SRAM):**
    * **CCM 권장 데이터:** **CPU만** 고속으로 접근하는 **Stack, ISR 시간-크리티컬 버퍼, RTOS 태스크 스택**
        * stack: 함수 호출 시 지역 변수, 인자 등을 두는 메모리라 접근 빈도가 높음
        * ISR 시간-크리티컬 버퍼: ISR이 인터럽트 안에서 읽고 쓰는 데이터(빨리 처리되어야 함)
        * RTOS 태스크 스택: 태스크마다 자기 전용 스택을 가지고 그 태스크 스택에 대해서 해당 태스크와 CPU만 접근함

    * <span class="hl-yellow">**CCM 절대 불가 데이터: DMA 전송 버퍼**</span> (UART/ADC/USB/Ethernet 수신 버퍼 등)
        * 이유:
            * CCM은 AHB 버스 매트릭스와 연결X(CPU랑만 연결) → DMA 하드웨어가 물리적으로 접근X → 데이터 수신X(근데 에러메시지도 안 남)
            * DMA 버퍼는 반드시 일반 SRAM(`0x2000_0000`)에 두어야

### 5. 가상 메모리/MMU vs MPU & 메모리 섹션 매핑

* **MMU ≠ MPU:**
    * **MMU:**
        * **Memory Management Unit**
        * Cortex-M에는 X
            * 가상 주소 → 물리 주소 변환에 따른 실행 시간 비결정성을 방지
            * 애초에 메모리 용량 작아서 가상화 필요X
    * **MPU:**
        * **Memory Protection Unit**
        * 주소 변환 X, **메모리 영역별 읽기/쓰기/실행 권한**만 보호

* **C 변수의** <span class="hl-yellow">**메모리 섹션**</span> **및 부팅 동작:**

    ```c
    int g_var = 10; // .data
    int g_zero; // .bss
    const int g_const = 5; // .rodata

    void func(){
        static int s_var = 20; // .data
        int local_var = 30; // Stack
    }
    ```

    * **SRAM에 저장되는 것**

        | 영역 | 내용 |
        |---|---|
        | Stack | 지역 변수 |
        | … | … |
        | Heap | 동적 할당 |
        | .bss | 0으로 초기화된(그냥 선언만 했거나/명시적으로 0으로 초기화) 전역/정적 변수 |
        | .data | 초기화된 전역, 정적 변수 |

        * 스택 오버플로우: 스택이 할당된 영역을 넘어 다른 영역을 덮어쓰는 현상
        * 동적 메모리 할당 위험한 이유
            * free 안 하면 메모리 누수
            * 할당, 해제 반복 → 메모리 단편화
            * 비결정적 실행 시간

            ⇒ **메모리 풀**

            : **고정 크기** 블록을 **미리 배열로 할당**해두고 필요할 때 쓰고 반납 → 단편화 문제, 비결정 문제 해결

    * **Flash에 저장되는 것**
        * **`.text`** **(Flash):**
            * 실행 코드
            * Flash에서 직접 실행 (XIP: Execute In Place)
        * **`.rodata`** **(Flash):** `const` 상수 및 문자열 리터럴
        * **`.data`** **(Flash → SRAM):**
            * 초기화된 전역/정적 변수
            * 전원이 꺼져도 유지되어야 하니까 Flash에 저장해놨다가 부팅 시 `startup.s`가 SRAM(VMA)으로 복사
                * <span class="hl-yellow">**복사해서 쓰는 이유3**</span>
                    1. 값을 되돌릴 수 없음(하나 되돌리려면 더 큰 단위로 지워야 함)
                    2. 수명 제한 있음
                    3. 원본을 잃음 → 리셋해도 원본 바뀐 상태 그대로

    * 링커 스크립트:
        * 컴파일된 코드와 데이터를 물리 메모리의 어디에 배치할지 지시하는 설정 파일
        * LMA, VMA
            * LMA(Load Memory Address): 전원이 꺼져도 유지되도록 칩(Flash)에 데이터를 구워두는 **저장 주소**
            * VMA(Virtual/Execution Memory Address): 프로그램 실행 중 변수가 실제로 읽고 쓰이는 **RAM 주소**
            * \> RAM AT \> FLASH:
                * 원본 초기값은 Flash(LMA)의 .data에 저장
                * 실행할 때는 RAM(VMA) 주소를 사용

                    ⇒ 부팅 시 `startup.s` 코드가 이 지시를 읽고 Flash의 초기값을 RAM으로 복사

    * 벡터 테이블

        | 오프셋 주소 (Flash) | 저장되어 있는 내용 (32bit 데이터) | 역할 |
        |---|---|---|
        | **`0x0800_0000`** **(0번지)** | **MSP (Main Stack Pointer) 초기값** | 부팅되자마자 사용할 스택의 탑 주소 (예: `0x2002_0000`) |
        | **`0x0800_0004`** **(4번지)** | **`Reset_Handler`** **주소** | 리셋 직후 CPU가 가장 먼저 달려가 실행할 시작 코드 주소 |
        | **`0x0800_0008 ~`** | **NMI, HardFault, SysTick 등** | 코어 내부 시스템 예외 핸들러 주소들 |
        | **`0x0800_0040 ~`** | **USART1, TIM2, EXTI 등** | 각 주변장치 하드웨어 인터럽트(IRQ) 핸들러 주소들 |

* 추가) SRAM, DRAM 비교
    * **SRAM (MCU 온칩):** 6T 셀 · Refresh 불필요 · 0 WS 결정론적 지연 · 소용량/고비용
    * **DRAM (PC/MPU 외장):** 1T1C 셀 · 각각 반대(64ms 주기 Refresh 필수 · 비결정적 지연 · 대용량/저비용)

**1. NAT (Network Address Translation)의 개념과 원리**

NAT는 IP 주소 고갈 문제를 완화하기 위해 도입된 기술

local network 내부의 모든 기기들이 외부 세계와 통신할 때 **단 하나의 IPv4 address (NAT IP address)를 공유**하여 사용하는 방식

- **Private IP address space:** Local network 내부에서는 `10/8`, `172.16/12`, `192.168/16`과 같이 내부망에서만 사용 가능한 사설 IP 주소 대역을 사용
- **NAT Implementation (동작 원리):** NAT router는 다음과 같은 과정을 수행
    1. **Outgoing datagrams:** 내부망에서 외부로 나가는 datagram의 기존 `(source IP address, port #)`를 `(NAT IP address, new port #)`로 변환. (변경은 이렇게 하고 내부에서 보낼 때는 진짜 그 목적지 주소와 포트로 보냄)
    2. **NAT translation table:** 변경한 `(source IP address, port #)`와 `(NAT IP address, new port #)`의 변환 쌍(translation pair)을 테이블에 기억
    3. **Incoming datagrams:** 외부 서버가 `(NAT IP address, new port #)`를 목적지로 해서 응답을 보내면, 라우터는 NAT table을 확인하여 원래의 내부 호스트 `(source IP address, port #)`로 변환한 뒤 전달
    - 즉, 외부로 나가는 모든 datagram은 **같은 source NAT IP address를 가지지만 서로 다른 source port numbers를 통해 구분**
    
    ⇒ LAN에서는 가짜(우리끼리만 쓰는 거)를 쓰고, 나갈 때는 진짜로 바꿈
    
    → LAN 내부 interface들은 변환한 줄을 모르고, 서버는 그냥 변환된 그 주소에서 오는 줄 앎
    

**2. NAT의 장점 (Advantages)과 논란 (Controversy)**

**장점 (Advantages):**

- ISP로부터 모든 기기를 **단 하나의 IP address (just one IP address)만 할당**받으면 됨
- 외부 세계에 알리지 않고도 local network 내부의 host 주소를 자유롭게 변경 가능
- 내부 기기들의 주소를 바꾸지 않은 채로 가입한 ISP를 변경 가능
- **Security (보안):** 내부망의 기기들이 외부에서 직접적으로 주소 지정되거나(directly addressable) 보이지(visible) 않으므로 안전

**논란 (Controversy) 및 한계:**

- 라우터는 Layer 3 (Network layer)까지만 처리해야 한다는 원칙을 위배. (네트워크 계층 장비가 Transport 계층의 port #를 조작하므로, end-to-end argument를 위반)
- IP 주소 부족 문제는 NAT와 같은 임시방편이 아니라 **IPv6**로 해결해야 한다는 비판
- **NAT traversal:** NAT 뒤에 숨어있는 클라이언트나 서버에 외부에서 직접 연결(connect)을 시도할 때 문제가 발생
- *NAT는 현재 가정, 기관, 4G/5G 네트워크 등에 광범위하게 쓰임*

**3. IPv6의 도입 배경 (Motivation)과 Datagram Format**

**도입 배경 (Motivation):**

- 32-bit인 IPv4 address space가 완전히 고갈
- 추가로 라우터의 처리/포워딩 속도(speed processing/forwarding)를 높이고, 네트워크 계층에서 "flows" 단위의 처리를 가능하게 하기 위해 도입

**IPv6 Datagram Format 및 IPv4와의 차이점:**

- **128-bit IPv6 address:** Source 및 destination 주소 공간이 128-bit로 대폭 확장
- **40-byte fixed length header:** 헤더의 길이를 **40-byte로 고정** → 어디까지가 헤더인지 확인할 필요 없음 → 처리 속도 향상
- **Flow label:** 같은 "flow"에 속하는 datagram들을 식별하는 데 사용
- **IPv4에서 사라진 기능들:**
    - **Checksum**
    - **Fragmentation / Reassembly**
    - **Options**

**4. IPv4에서 IPv6로의 전환 (Transition): Tunneling**

전 세계의 모든 라우터를 정해진 날("flag days")에 동시에 업그레이드하는 것은 불가능

⇒ Tunneling (터널링)으로 해결

- **Tunneling 개념:** 두 개의 IPv6 라우터 사이에 IPv4 네트워크 망이 있을 때, IPv6 datagram 전체를 IPv4 datagram의 payload 영역 안에 캡슐화(encapsulation) ⇒ 전송 ("packet within a packet")
- 송신 측 IPv6/v4 호환 라우터에서 IPv4 포장지로 감싸 전송하고, 수신 측 IPv6/v4 라우터에 도착하면 포장을 뜯어 원래의 IPv6 datagram을 확인하여 목적지로 전달

**5. IPv6 채택 (Adoption) 현황**

- Google 통계(2023)에 따르면 클라이언트의 약 40%가 IPv6를 통해 서비스에 접근
- NIST에 따르면 미국 정부 도메인(US government domains)의 1/3이 IPv6를 지원
- 하지만 완전한 도입과 전개(deployment)까지는 25년 이상 소요될 전망

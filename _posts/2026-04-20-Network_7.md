**1. TCP 개요 및 주요 특징**

- **1대1 통신 (Point-to-point):** 단일 송신자와 단일 수신자 간의 통신
- **신뢰적이고 순서가 보장된 바이트 스트림 (Reliable, in-order byte stream):** 애플리케이션 데이터를 메시지 경계 없이 연속적인 바이트 스트림으로 취급
- **전이중 통신 (Full duplex data):** 동일한 연결 내에서 양방향으로 데이터가 흐를 수 있으며, MSS(Maximum Segment Size)를 통해 최대 세그먼트 크기를 제한
    - **누적 확인 응답 (Cumulative ACKs):** 수신자는 자신이 연속적으로 정상 수신한 데이터까지를 누적하여 확인 응답 ⇒ 이전 ACK loss돼도 다음 ACK으로 커버 가능
- **파이프라이닝 (Pipelining):** 혼잡 제어 및 흐름 제어를 통해 윈도우 크기를 동적으로 설정하여 여러 패킷을 동시에 전송
- **연결 지향형 (Connection-oriented):** 데이터 교환 전 핸드셰이킹(제어 메시지 교환)을 통해 송수신자의 상태를 초기화
- **흐름 제어 (Flow controlled):** 송신자가 수신자의 처리 속도를 압도(overwhelm)하지 않도록 제어

**2. TCP 세그먼트 구조**
TCP 세그먼트는 헤더와 데이터(페이로드) 영역으로 나뉘며, 주요 헤더 필드는 다음과 같음

![TCP 세그먼트 구조: source/dest port #, sequence number, acknowledgement number, header length/flags(C E U A P R S F)/receive window, checksum/urgent data pointer, options, application data 순으로 배치된 헤더](/assets/img/posts/Network_7/image-9.png)

- **출발지/목적지 포트 번호 (Source/Dest port #):** 다중화/역다중화를 위해 사용
- **Sequence number:** 세그먼트 데이터의 '첫 번째 바이트'가 갖는 바이트 스트림 번호 (패킷 번호가 아님)
- **확인 응답 번호 (Acknowledgement number):** 상대방으로부터 수신하기를 **기대하는 다음 바이트 번호**
- **플래그 비트:** 연결 관리를 위한 `RST`, `SYN`, `FIN`, 그리고 `ACK` 비트 등이 포함
- **수신 윈도우 (Receive window, rwnd):** 흐름 제어를 위해 수신자가 현재 수용할 수 있는 버퍼의 남은 공간 크기(바이트)를 명시
- 기타: 헤더 길이(Length), 체크섬(Checksum), 옵션(Options) 등

**3. TCP RTT 측정과 타임아웃 설정**
타임아웃은 RTT보다 커야 하지만, 네트워크 상태에 따라 RTT가 계속 변하므로 이를 적절히 예측해야 함 (너무 짧으면 불필요한 재전송이 발생하고, 너무 길면 패킷 손실에 둔감해짐)

- **EstimatedRTT (예측된 RTT):** 새로 측정한 `SampleRTT`와 기존 `EstimatedRTT`를 EWMA(지수 가중 이동 평균) 방식으로 결합하여 부드럽게(smooth) 처리 (재전송된 패킷의 RTT는 무시)
    
    EstimatedRTT=(1−*α*)×EstimatedRTT+*α*×SampleRTT
    
- **DevRTT (RTT 편차):** `SampleRTT`와 `EstimatedRTT` 간의 편차에 대한 EWMA
    
    DevRTT=(1−*β*)×DevRTT+*β*×∣SampleRTT−EstimatedRTT∣
    
- **타임아웃 간격 (TimeoutInterval):** `EstimatedRTT + 4 * DevRTT` 공식을 사용하여, 예측값에 '안전 마진(Safety margin)'을 더해 설정

**4. TCP 송수신자의 동작 원리**

- **송신자 (Sender):**
    - 애플리케이션에서 데이터를 받으면 순서 번호를 부여하여 세그먼트를 생성, 타이머가 돌고 있지 않다면 '가장 오래된, 응답받지 못한 세그먼트'를 기준으로 타이머를 시작
    - 타임아웃 발생 시 해당 세그먼트를 재전송하고 타이머를 재시작
    - ACK를 수신하면 상태를 업데이트, 아직 응답받지 못한 세그먼트가 남아있다면 타이머를 다시 시작
- **수신자 (Receiver)의 ACK 생성 (RFC 5681):**
    - 순서에 맞는 세그먼트가 도착했고 이전 데이터가 모두 ACK 되었다면, 다음 세그먼트를 위해 최대 500ms까지 기다리는 **지연된 ACK(Delayed ACK)**를 사용 (뭉쳐서 보내려고)
    - 기다리던 중 다음 순서의 세그먼트가 도착하면 즉시 **단일 누적 ACK**를 전송
    - 순서가 어긋난(out-of-order) 세그먼트가 도착해 '간격(gap)'이 감지되면, 자신이 기대하는 다음 순서 번호를 담은 **중복 ACK(Duplicate ACK)를 즉시 전송**

**5. 재전송 시나리오와 빠른 재전송 (Fast Retransmit)**

- **재전송 시나리오:** ACK가 유실되더라도 이어지는 패킷에 대한 누적 ACK가 성공적으로 도착하면 과거의 데이터까지 수신된 것으로 인정되므로 불필요한 재전송을 방지 (누적 ACK의 장점). 또한, 타임아웃이 너무 일찍 발생해(Premature timeout) 재전송되더라도 수신자는 누적 ACK로 대응
- **빠른 재전송 (Fast Retransmit):** 타임아웃 시간은 대체로 길기 때문에, 손실 복구 지연을 줄이기 위해 도입. 수신자가 순서가 어긋난 패킷을 받을 때마다 중복 ACK를 전송, 송신자가 동일한 데이터에 대해 **3개의 중복 ACK (총 4개의 동일한 ACK)**를 받으면 타임아웃을 기다리지 않고 즉시 해당 세그먼트를 재전송

**6. TCP 흐름 제어 (Flow Control)**

- 네트워크 계층에서 데이터가 도착하는 속도가 애플리케이션이 소켓 버퍼에서 데이터를 읽어가는 속도보다 빠를 때, 수신 버퍼가 오버플로우되는 것을 방지하는 매커니즘 → 그러면 loss되니까
- 수신자는 TCP 헤더의 **`rwnd` (receive window) 필드**를 통해 현재 수신 버퍼에 남은 여유 공간 크기(`RcvBuffer - 버퍼링된 데이터`)를 송신자에게 지속적으로 통보
- 송신자는 아직 확인 응답받지 않은 데이터("in-flight" 데이터)의 양을 수신자가 알려준 `rwnd` 값 이하로 제한하여 오버플로우를 원천 차단

**7. 연결 관리 (Connection Management)**
신뢰할 수 없는 네트워크에서는 패킷 지연이나 순서 바뀜 때문에 단순한 '2-way handshake'를 쓰면 반쪽짜리 연결(Half-open connection)이나 중복 데이터 수용 문제가 발생 (→ 서로 상태 모름). 이를 방지하기 위해 **3-way handshake**를 사용

![TCP 3-way handshake: 클라이언트는 SYNSENT→ESTAB, 서버는 LISTEN→SYN RCVD→ESTAB으로 상태가 전이되며 SYN(Seq=x) → SYNACK(Seq=y, ACKnum=x+1) → ACK(ACKnum=y+1) 순서로 세그먼트를 교환](/assets/img/posts/Network_7/image-10.png)

- **연결 설정 (3-way Handshake):**
    1. **SYN:** 클라이언트가 초기 순서 번호(x)를 선택해 `SYNbit=1`인 SYN 세그먼트를 서버로 전송 (클라이언트 상태: `SYNSENT`)
    2. **SYNACK:** 서버가 이를 수락하고 자신의 초기 순서 번호(y)를 선택한 뒤, `SYNbit=1, ACKbit=1, ACKnum=x+1`인 SYNACK 세그먼트를 응답 (서버 상태: `SYN RCVD`)
    3. **ACK:** 클라이언트가 서버의 SYNACK에 대해 `ACKbit=1, ACKnum=y+1`인 ACK 세그먼트를 전송. 이때부터 페이로드에 데이터를 담아 보낼 수 있음 (클라이언트/서버 상태: `ESTAB`)
- **연결 종료:**
    - 클라이언트와 서버는 각자의 방향에서 연결을 닫기 위해 `FIN bit=1`인 세그먼트를 전송
    - 상대방의 FIN을 받으면 ACK로 응답, 자신의 FIN 전송과 ACK 응답을 동시에 결합하여 보낼 수도 있음. 양쪽에서 동시에 FIN을 교환하는 상황도 정상적으로 처리됨

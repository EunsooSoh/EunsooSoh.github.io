## 5. Evaluation

### 5.1 Simulation methodology

* 전체 flash system 구조(Fig. 1)에서 4절의 FTL 알고리즘들을 구현
* physical flash memory 계층은 실제 flash와 같은 특성을 가진 flash emulator로 시뮬레이션
* file system 계층은 **FAT file system**을 가정 (임베디드 시스템에서 널리 쓰임)
    * FAT의 disk 구성 (Fig. 13): boot sector, file allocation table(FAT 1, FAT 2), root directory entries, files

    ![Fig 13](/assets/img/posts/FTL_6/image.png){: .s70 }
    
    * boot sector, FAT, root directory에 해당하는 logical 영역은 volume files보다 접근 빈도가 높음
* 시뮬레이션 방법
    * FAT file system이 file write 요청을 받았을 때 block device driver에 내리는 access pattern을 수집
    * 실제 워크로드 두 가지의 결과를 보고
        * Symbian: Symbian OS에서 1MB 파일을 복사하는 워크로드
        * Digicam: 디지털 카메라 워크로드
    * 두 워크로드의 특성
        * Digicam: 
            * 대부분 sequential. 
            -> 작은 random write와 빈번하고 큰 sequential write로 구성
        * Symbian: 
            * random pattern이 많음. 
            -> 많은 random write와 빈번하지 않고 큰 sequential write로 구성
* 비교 대상 (그래프 범례): FMAX, LOG, MSBS, SSR, Sector

    * 그래프 축
        * x축: test count (워크로드를 반복 수행한 횟수)
        * y축: 총 elapsed time (ms)
    * 워크로드 하나는 크기가 작아서 한 번 수행해서는 flash가 차지 않음 → flash가 채워진 상태에서의 특성을 보려고 워크로드를 여러 번 반복. 처음에는 flash가 비어 있다가 test count가 늘수록 점점 참
    * 결과: **Log block scheme이 가장 좋은 성능**
        * RAM을 많이 쓰는 sector mapping보다도 좋음
        * 이유: Digicam 워크로드는 대부분 sequential write이고, Log scheme은 sequential write pattern에서 거의 이상적으로 동작
        * sector mapping은 LSN-to-PSN 매핑 테이블을 쓰기 때문에 logical sector가 overwrite될 때마다 매핑 테이블의 변경을 flash에 써야 함. Log scheme은 LBN-to-PBN 매핑이라 이런 일이 덜 발생
        * 실험에서 1 block = 32 sector이므로, LSN-to-PSN 테이블은 LBN-to-PBN 매핑보다 약 30배 더 자주 갱신해야 함
        * 그래서 sector mapping은 erase는 더 적게 하지만(Fig. 15), 전체 실행 시간은 Log scheme보다 김
    * **SSR**은 다른 기법보다 성능이 나쁨
        * 하나의 logical block이 하나의 physical block에만 매핑되기 때문
        * SSR에서 block을 erase할 때는 유효한 sector가 많아서 copy 연산이 많이 필요하고, erase된 block이 앞으로 다시 erase될 확률도 매우 높음
        * logical block을 둘 이상의 block에 매핑할 수 있게 하면(Log scheme, FMAX) 성능이 좋아짐
    * **Mitsubishi**는 logical block이 physical block 하나에 매핑되지만, space sector가 또 다른 block의 역할을 함
        * 같은 워크로드를 반복하기 때문에 merge 연산이 주기적으로 필요해서, 총 elapsed time에 주기적인 감소(drop)가 나타남
    * Log scheme이 FMAX와 Mitsubishi보다 좋은 이유: random write를 처리하는 log block이 소수라서 Log scheme의 merge 알고리즘이 더 효율적
    * Fig. 15 (erase count)의 결과는 elapsed time과 비슷함 (erase count가 전체 성능에서 가장 지배적인 요인이기 때문)
        * 한 연구에 따르면 read(1 page) : write(1 page) : erase(1 block)의 실행 시간 비율은 약 **1 : 7 : 63**
        * **sector mapping이 erase 횟수가 가장 적음**
            * logical sector를 아무 free physical sector에나 매핑할 수 있기 때문
            * 대부분의 block이 invalid data로만 차 있거나 valid data로만 차 있어서, valid sector가 있는 block들 사이의 merge가 드물고 erase가 줄어듦

## 6. Conclusion

* address mapping 방식별 정리
    * **sector mapping**: free sector가 있으면 erase를 최대한 미룰 수 있어서 erase-before-write를 가장 잘 극복하지만, 매핑 정보가 많이 필요해서 임베디드 응용에는 적용하기 어려움
    * **block mapping**: 매핑 정보가 가장 적게 필요하지만(sector 보다 큰 block 단위의 매핑 정보를 저장하기 때문에), 
    같은 logical sector number를 자주 갱신하면 성능이 매우 나쁨
    * **hybrid mapping**: 같은 logical sector를 자주 갱신하는 문제를 해결하지만, block mapping보다 매핑 정보가 더 필요함
* 매핑 정보 관리 방식은 **map block method**와 **per block method**로 분류
    * map block method: 매핑 정보를 저장할 전용 block이 여러 개 필요
    * per block method: 각 block에 매핑 정보를 저장
* FTL을 구현할 때는 RAM 사용량도 중요. RAM에는 logical-to-physical 매핑 정보, free memory space 정보, wear-leveling 정보를 저장
* FMAX, sector mapping, Log scheme, SSR, Mitsubishi를 구현해서 성능 결과를 제시
    * logical block을 physical block 하나에만 매핑하면(SSR) 성능이 나쁨
    * space sector(Mitsubishi)와 replacement block(FMAX)을 쓰면 성능을 개선할 수 있음
    * logical block을 둘 이상의 block에 매핑할 수 있으면 merge 연산이 전체 성능의 핵심 요인이 됨
    * Log scheme은 소수의 log block과 많은 data block을 쓰는 좋은 해법

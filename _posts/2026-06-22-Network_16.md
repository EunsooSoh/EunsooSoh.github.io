**1. Traditional Routing vs. SDN (도입 배경)**

- **Traditional (Per-router control):** 역사적으로 인터넷 네트워크 계층은 각 라우터마다 개별적으로 제어되는 분산형 방식을 사용. 라우터는 switching hardware와 독점적인(proprietary) OS(예: Cisco IOS) 및 라우팅 프로토콜이 하나의 박스 안에 통합된 **monolithic(단일 구조)** 형태
- **SDN (Software-Defined Networking):** 원격 컨트롤러(Remote controller)가 포워딩 테이블을 계산하고 라우터에 설치하는 논리적인 중앙 집중형 제어 방식(**Logically centralized control**)
    - **도입 이유 (Why SDN?):**
        1. **Easier network management:** 라우터의 설정 오류(misconfigurations)를 방지하고, 트래픽 흐름(traffic flows)의 유연성을 크게 향상
        2. **Table-based forwarding:** OpenFlow와 같은 API를 통해 중앙에서 쉽게 라우터를 "programming"할 수 있음
        3. **Open implementation:** 폐쇄적인 환경을 벗어나 누구나 control plane(라우팅)을 구현할 수 있음

**2. SDN Architecture (SDN 아키텍처의 3가지 계층)**

SDN 구조 3계층

**① Data-plane switches (데이터 평면 스위치)**

- 빠르고 단순한 범용(commodity) 스위치로, 하드웨어 단에서 **generalized forwarding**을 수행
- 컨트롤러의 감독하에 **flow (forwarding) table**을 계산받아 설치

**② SDN Controller (네트워크 운영체제, Network OS)**

- 네트워크의 상태 정보(**network state information**)를 관리하고 유지
- 성능, 확장성(scalability), 결함 허용(fault-tolerance)을 위해 물리적으로는 여러 대의 서버로 구성된 **distributed system(분산 시스템)**으로 구현
- **Northbound API:** 위의 네트워크 제어 앱들과 상호작용하는 인터페이스 (예: RESTful API)
- **Southbound API:** 아래의 스위치들과 통신하는 인터페이스 (예: OpenFlow, SNMP)

**③ Network-control apps (네트워크 제어 애플리케이션)**

- 실질적인 통제의 "두뇌(brains)" 역할. 라우팅(routing), 접근 제어(access control), 로드 밸런싱(load balance) 등의 기능을 구현
- **Unbundled:** SDN 컨트롤러 제공자나 라우터 벤더와 독립적으로 제3자(3rd party)가 개발하고 제공 가능

**3. OpenFlow Protocol (오픈플로우 프로토콜)**

SDN 컨트롤러와 스위치 사이(Southbound)에서 작동하는 통신 규약

- **TCP** 연결을 사용하여 메시지를 교환, 선택적으로 암호화(encryption)를 지원
- **주요 메시지 종류:**
    - **Controller-to-switch:** 컨트롤러가 스위치의 기능을 묻거나(features) 설정할 때 사용
    - **Asynchronous (Switch-to-controller):** 스위치가 컨트롤러에게 알림을 보냄
        - `packet-in`: 스위치 테이블에 없는 패킷이 들어왔을 때 컨트롤러로 패킷을 전송
        - `flow-removed`: 스위치에서 플로우 테이블 항목이 지워졌음을 알림
        - `port status`: 특정 포트의 링크 상태 변화(예: 링크 끊어짐)를 알림

---

**4. SDN Control/Data Plane Interaction Example (동작 시나리오)**

링크가 끊어졌을 때 다익스트라 알고리즘이 SDN에서 어떻게 동작하는지 보여주는 예시

1. 스위치($S_1$)가 링크 실패(link failure)를 감지하고 OpenFlow **port status** 메시지를 컨트롤러에 전송
2. SDN 컨트롤러는 이 메시지를 받고 내부의 **link status info**(네트워크 상태 정보)를 업데이트
3. 상태가 변경되었으므로, Northbound API를 통해 상위의 Routing app(다익스트라 알고리즘)이 호출됨
4. Routing app은 업데이트된 네트워크 상태를 바탕으로 새로운 최적의 경로를 계산
5. Routing app이 컨트롤러의 Flow table 관리 컴포넌트와 상호작용
6. 컨트롤러는 OpenFlow를 사용하여 업데이트가 필요한 스위치들에게 새로운 **flow table**을 내려보내 설치(install)

**5. 실제 SDN 컨트롤러 구현 사례**

- **Google ORION:** 구글의 데이터센터(Jupiter)와 Wide area(B4) 네트워크를 위한 SDN 제어 평면. 구글 내부(intradomain) 라우팅과 트래픽 엔지니어링을 수행하며, 계약된 SLA(서비스 품질)를 맞추기 위해 CoFlow 스케줄링 등을 관리
- **OpenDaylight (ODL) Controller:** 다양한 내부 모듈(Traffic engineering, Firewalling 등)과 남/북단 API를 연결해 주는 **Service Abstraction Layer (SAL)** 구조가 특징

**6. Network Management & Configuration (네트워크 관리 및 설정)**

수많은 네트워크 장비를 관리(Manage)하기 위해 관리 서버와 Managed device 간에 사용하는 기술들

- **CLI (Command Line Interface):** 관리자가 SSH 등을 통해 개별 장비에 직접 타이핑하거나 스크립트를 입력하는 전통적 방식
- **SNMP (Simple Network Management Protocol) / MIB:**
    - 관리자가 SNMP 프로토콜을 사용해 각 기기의 **MIB (Management Information Base)** 데이터를 조회(query)하거나 설정(set)
    - **MIB:** 기기의 작동 및 설정 데이터들이 모여 있는 곳으로, **SMI (Structure of Management Information)**라는 데이터 정의 언어로 작성 (예: UDP 전송 성공/실패 횟수 카운터 등)
- **NETCONF / YANG:**
    - 최근 도입되는 방식으로, 단일 기기를 넘어 네트워크 전체(**network-wide, holistic**)의 여러 기기 설정을 동시에 처리(atomic-commit)하는 데 중점
    - **YANG:** 설정 데이터를 정의하는 **data modeling language**
    - **NETCONF:** YANG 호환 데이터를 스위치와 교환하는 프로토콜. 안전하고 신뢰할 수 있는(secure, reliable) 전송(TLS) 위에서 **RPC (Remote Procedure Call)** 패러다임과 XML 인코딩을 사용

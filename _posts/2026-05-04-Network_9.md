**1. 혼잡 제어(Congestion Control)의 기본 원리**

혼잡(Congestion): 너무 많은 송신자가 네트워크가 감당할 수 없을 만큼 많은 데이터를 너무 빠르게 보낼 때, 라우터 버퍼 오버플로우로 인한 패킷 손실(Packet loss)과 긴 큐잉 지연(Queueing delay)이 발생하는 것

이를 해결하기 위해 TCP는 **AIMD (Additive Increase, Multiplicative Decrease)** 방식을 사용하여 가용 대역폭을 지속적으로 탐색(Probing)하며, 이로 인해 전송률 그래프가 톱니바퀴(Sawtooth) 모양을 그림

- **선형 증가 (Additive Increase):** 패킷 손실이 감지되기 전까지 매 RTT마다 송신 윈도우 크기(`cwnd`)를 1 MSS(최대 세그먼트 크기)씩 선형적으로 늘림
- **지수적 감소 (Multiplicative Decrease):** 패킷 손실 이벤트가 발생하면 즉시 현재의 송신 속도(`cwnd`)를 절반으로 대폭 줄임
- 이러한 AIMD는 분산되고 비동기적인 알고리즘으로서, 네트워크 전체의 혼잡 흐름을 최적화하고 안정성을 유지하는 효과

**2. TCP 혼잡 제어의 상세 동작 (FSM 상태 전환)**

TCP 송신자

- 자신의 전송량 한도를 `LastByteSent - LastByteAcked <= cwnd`로 제한
- 대략 `cwnd / RTT` (bytes/sec)의 속도로 데이터를 전송
- 혼잡 제어는 다음의 세 가지 상태를 오가며 동작. ++ 이벤트 발생하는 순간 그 다음 상태라고 보면 됨

![TCP 혼잡 제어 FSM: slow start, congestion avoidance, fast recovery 세 상태를 new ACK/duplicate ACK/timeout 이벤트에 따라 순환하며, 각 상태 전이마다 cwnd와 ssthresh 갱신 규칙이 표시된 다이어그램](/assets/img/posts/Network_9/image.png)

**① Slow Start (슬로우 스타트)**

- 연결이 처음 시작될 때 `cwnd`를 1 MSS로 초기화하여 느리게 시작
- 하지만 확인 응답(ACK)을 하나 받을 때마다 `cwnd`를 늘리므로, 매 RTT마다 전송 속도가 **Exponentially 두 배씩 급격하게 증가**. (doubling)

**② Congestion Avoidance (혼잡 회피)**

- `cwnd` 값이 임계값인 **`ssthresh`**(처음을 제외하고 패킷 손실 직전 `cwnd`의 절반 값) 이상이 되면, 지수적 증가를 멈추고 **매 RTT마다 1 MSS씩 선형적으로 천천히 증가**

**③ 패킷 손실 감지에 따른 동작 (Tahoe vs. Reno)**
패킷 손실의 원인에 따라 대처 방식이 나뉨

- **타임아웃(Timeout) 발생 시:** 아주 심각한 혼잡으로 간주하여 `ssthresh`를 현재 `cwnd`의 절반으로 줄임. 그리고 **`cwnd`를 1 MSS로 초기화**한 뒤 Slow Start 상태로 전이 (TCP Tahoe, TCP Reno 공통)
- **3개의 중복 ACK 수신 시 (Fast Retransmit):** 네트워크가 일부 동작하고 있다고 판단
    - **TCP Reno:** `ssthresh`를 `cwnd`의 절반으로 줄이고, **`cwnd` 역시 현재 `ssthresh` + 3으로만 줄인 후**, Fast Recovery 상태로 진입
    - **TCP Tahoe:** 타임아웃과 마찬가지로 `cwnd`를 **항상 1MSS**로 초기화한 후, slow start 상태로 진입

**④ Fast Recovery (빠른 회복, TCP Reno)**

- 누락된 패킷을 재전송하며, 중복 ACK가 올 때마다 `cwnd`를 1 MSS씩 증가시켜 새 세그먼트를 전송
- 누락되었던 패킷에 대한 새로운 정상 ACK가 도착하면, `cwnd`를 낮춰둔 `ssthresh` 값으로 변경하고 **혼잡 회피(Congestion Avoidance)** 상태로 복귀

- ssthresh는 무조건 절반이 되기만 함
- timeout → 윈도우 1, 3dup ACK → 윈도우 ssthresh + 3

**3. 향상된 TCP 혼잡 제어 방식**

**① TCP CUBIC (최신 웹 서버 및 Linux 기본값)**

- 손실이 발생했을 때(3dup ACK이나 timeout 등으로 간접 파악)의 윈도우 크기를 $W_{max}$로 기억
- 혼잡 회피 상태에서 목표치인 $W_{max}$에 도달하기 전까지는 **시간의 3차 함수(Cube) 그래프 형태를 따라 윈도우를 매우 빠르게 키우고**, $W_{max}$에 근접할수록 조심스럽게 천천히 늘려 가용 대역폭을 더 똑똑하게 탐색

![TCP Reno와 TCP CUBIC의 전송률 변화 비교 그래프: Reno는 손실마다 절반으로 떨어졌다가 선형(톱니)으로 증가하는 반면, CUBIC은 Wmax 근처에서 완만해지는 3차 함수 곡선을 따라 증가하다 넘어서면 다시 빠르게 증가](/assets/img/posts/Network_9/image-1.png)

**② 지연 기반(Delay-based) TCP (예: BBR)**

- TCP의 송신 속도를 맹목적으로 늘리면 종단 간 처리량이 늘어나는 것이 아니라 병목 라우터의 버퍼만 채워 측정 RTT(지연)만 길어짐
- 파이프를 "가득 채우되 넘치지는 않게(just full = throughput 최대화, but no fuller = delay 낮게)" 유지하는 것을 목표로 함
- 가장 덜 혼잡했을 때의 최소 RTT(`RTTmin = minimum observed RTT`)를 기준으로 예측한 최적 throughput(`cwnd` / `RTTmin`)과 현재 측정된 throughput을 비교
    
    $measured\ throughput = \frac{bytes\ sent\ in\ last\ RTT\ interval}{RTT_{measured}}$
    
    - 두 값이 비슷하면 혼잡하지 않다고 보고 윈도우를 선형 증가
    - 측정 throughput이 턱없이 부족하면 혼잡이 발생했다고 판단해 윈도우를 선형 감소

**4. ECN (Explicit Congestion Notification)**

- 종단 호스트끼리 패킷 손실로 혼잡을 유추하는 것을 넘어, **네트워크 핵심부의 라우터가 혼잡 상태를 직접 명시적으로 알려주는 기능**. ⇒ by network router
- 라우터가 혼잡을 감지하면 IP **데이터그램** 헤더(ToS 필드)의 ECN 비트(2 bits)를 11로 마킹하여 전달
- 이를 수신한 목적지 호스트는 TCP **ACK 세그먼트**의 **ECE 비트**를 1로 설정하여 송신자에게 혼잡 상황을 경고

![ECN 동작 다이어그램: 라우터가 혼잡을 감지해 IP 데이터그램의 ECN 비트를 10으로 마킹하고, 목적지가 TCP ACK 세그먼트의 ECE 비트를 1로 설정해 출발지에게 되돌려 보내는 흐름](/assets/img/posts/Network_9/image-2.png)

**5. TCP의 공평성 (TCP Fairness)**

- **개념:** 대역폭이 $R$인 병목 링크를 $K$개의 TCP 연결이 공유할 때, 각각 평균적으로 $R/K$의 대역폭을 나누어 가짐 (connection마다 동등하게 전송률을 분배하지만, host 기준으로는 다를 수 있음)
- **공평성을 위협하는 요인:**
    - **UDP:** 혼잡 제어를 하지 않고 일정한 속도로 데이터를 전송하며 패킷 손실을 무시하므로, 대역폭을 양보하는 TCP의 파이를 뺏어감
    - **병렬 TCP 연결 (Parallel connections):** 특정 애플리케이션(예: 웹 브라우저)이 고의로 여러 개의 TCP 연결을 동시에 열어버리면, 링크의 대역폭을 훨씬 더 많이 차지 (예: 9개의 연결이 있는 곳에 혼자 11개의 TCP를 열면 대역폭의 절반 이상을 차지함(11/20))

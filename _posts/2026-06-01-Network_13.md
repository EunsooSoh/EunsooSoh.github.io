**1. Generalized Forwarding (일반화된 포워딩)**

기존의 목적지 IP 주소 기반 포워딩을 넘어, 여러 계층의 헤더 필드를 기반으로 동작하는 유연한 패킷 처리 방식

- **"Match plus action":** 들어오는 패킷 헤더의 비트들을 특정 패턴과 **match**하고, 그 결과에 따라 지정된 **action**을 수행
- **Forwarding table(Flow table):** 라우터의 match+action 규칙들을 정의한 테이블
    - **Flow:** link-, network-, transport-layer 등 다양한 헤더 필드의 값들에 의해 정의
    - **Match:** packet header fields의 pattern values를 확인(와일드카드 사용 가능)
    - **Action:** matched packet에 대해 **drop, copy, forward, modify** 하거나, **send matched packet to controller** 동작을 수행
    - **Priority:** 겹치는 패턴이 있을 때 우선순위를 결정
    - **Counters:** 처리된 bytes와 packets의 수
- **Network programmability:** 이를 통해 네트워크 전체의 동작을 "program"할 수 있음

**2. OpenFlow와 Match+Action의 통합 활용**

OpenFlow 프로토콜: match+action 구조를 활용하는 SDN의 프로토콜

![OpenFlow 헤더 매칭 필드: Ingress Port, Src/Dst MAC, Eth Type, VLAN ID/Pri(링크 계층), IP Src/Dst/Proto/ToS(네트워크 계층), TCP/UDP Src/Dst Port(트랜스포트 계층)로 구성된 매칭 필드 구조](/assets/img/posts/Network_13/image-1.png)

![Destination-based forwarding과 Firewall 규칙 예시: IP Dst=51.6.0.8이면 port 6으로 forward, TCP d-port=22면 drop, IP Src=128.119.1.1이면 drop하는 3개의 match+action 규칙](/assets/img/posts/Network_13/image-2.png)

![Layer 2 destination-based forwarding 예시: MAC dst=22:A7:23:11:E1:02만 매칭해 port 3으로 forward하는 규칙](/assets/img/posts/Network_13/image-3.png)

- **Header fields to match:**
    - **Link layer:** Ingress Port, Src MAC, Dst MAC, Eth Type, VLAN ID, VLAN Pri
    - **Network layer:** IP Src, IP Dst, IP Proto, IP ToS
    - **Transport layer:** TCP/UDP Src Port, TCP/UDP Dst Port
- **OpenFlow:** 하나의 장비가 설정에 따라 여러 역할을 수행 가능
    - **Router:** **match** (longest destination IP prefix) → **action** (forward out a link)
    - **Switch:** **match** (destination MAC address) → **action** (forward or flood)
    - **Firewall:** **match** (IP addresses and TCP/UDP port numbers) → **action** (permit or deny / drop)
    - **NAT:** **match** (IP address and port) → **action** (rewrite address and port)
        - 예
            - **Match (조건):** 목적지 IP(Dst IP) == 203.0.113.5 이고, 목적지 포트(Dst Port) == 10001 인 패킷이 들어오면
            - **Action (행동):** 목적지 IP를 192.168.1.100 (원래 내부 PC)로 덮어쓰고(modify), 목적지 포트를 3333 (원래 PC 포트)로 덮어쓴 뒤, 내부망과 연결된 포트(예: Port 2)로 내보냄(Forward)
- **Orchestrated tables:** 중앙의 OpenFlow 컨트롤러가 여러 스위치의 flow table을 조율하여, 특정 호스트 간의 패킷이 원하는 경로로만 다니도록 **network-wide behavior**를 program할 수 있음

**3. Middleboxes (미들박스)**

- **Definition (RFC 3234):** source host와 destination host 사이의 데이터 경로 상에서, 표준 IP 라우터의 기능 이외의 다른 기능을 수행하는 중간 장비(intermediary box)
- **Middleboxes everywhere (종류 및 위치):** 네트워크 곳곳에 존재
    - **NAT:** home, cellular, institutional 네트워크
    - **Firewalls, IDS:** corporate, institutional, service providers, ISPs
    - **Load balancers:** corporate, data center, mobile nets
    - **Caches / Application-specific:** service provider, CDNs
- **Evolution (미들박스의 진화 방향):**
    - 초기: 독점적이고 폐쇄적인 솔루션
    - 변화: open API를 구현하는 **"whitebox" hardware**로 이동, 소프트웨어 혁신으로 확장
    - **Programmable local actions:** match+action을 통한 로컬 동작의 프로그래밍을 지원
    - **SDN:** private/public cloud 환경에서 논리적으로 중앙 집중화된 제어(**centralized control**) 및 설정을 수행
    - **NFV (Network functions virtualization):** white box의 networking, computation, storage 인프라 위에서 다양한 네트워크 서비스들을 소프트웨어 기반(programmable services)으로 가상화하여 구현

**4. Internet Architecture**

- **The IP hourglass (IP 모래시계 모델):** 인터넷 아키텍처는 응용/링크 계층에는 다양한 프로토콜(HTTP, SMTP, RTP, QUIC, DASH… / Ethernet, PPP, PDCP, WiFi, Bluetooth…)이 존재하지만, 그 사이 네트워크 계층은 IP라는 **단 하나의 프로토콜**로 좁아지는 "가는 허리" 구조. IP는 모든 인터넷 연결 기기에 반드시 구현되어야 함

![인터넷의 모래시계(hourglass) 모델: 위쪽 응용 계층(HTTP, SMTP, RTP, QUIC, DASH 등)과 아래쪽 물리/링크 계층(copper, radio, fiber, Ethernet, WiFi 등)이 다양한 반면, 트랜스포트(TCP/UDP)를 거쳐 네트워크 계층은 IP 하나로 좁아지는 모래시계 형태](/assets/img/posts/Network_13/image-4.png)

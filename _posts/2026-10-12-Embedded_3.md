### 1. ISA, 프로세서, RISC 철학

#### 1) ISA vs Processor IP vs Chip (3단계 위계 구별)

* **ISA** (Instruction Set Architecture, 설계 규격서):
    * 소프트웨어와 하드웨어 사이의 계약서
    * 명령어 집합, 데이터 처리 방식, 레지스터 동작 규칙 등을 정의
* **Processor IP** (프로세서 설계도):
    * ISA 규격을 실제로 작동하도록 구현한 논리 회로 설계도(Soft IP)
    * ex. ARM Cortex-M4
* Chip / MCU (완성 칩): ARM의 프로세서 코어에 제조사(ST 등)가 주변장치(GPIO, UART, ADC, Timer)와 메모리(Flash, SRAM)를 결합하여 제작한 최종 실물 반도체. (예: STM32F407)

<details markdown="1">
<summary>데이터시트 읽기:</summary>

레지스터/명령어 등 Core 관련 내용은 **ARM 문서**를, GPIO/ADC 등 주변장치 내용은 **ST 데이터시트**를 참조.

</details>

#### 2) RISC vs CISC (임베디드에 RISC가 적합한 이유)

| 비교 항목 | RISC (Reduced Instruction Set Computer) | CISC (Complex Instruction Set Computer) |
| --- | --- | --- |
| **명령어 구조** | <span class="hl-yellow">**단순**</span>하며 <span class="hl-yellow">길이가 고정</span>됨 (16/32비트) | 복잡하며 가변 길이를 가짐 (1~15바이트) |
| **메모리 접근** | **Load/Store 구조** (`LDR`/`STR` 전용 명령어만 접근) | 메모리와 레지스터 간 직접 연산 가능 (`ADD EAX, [mem]`) |
| **레지스터 수** | 넉넉함 (**ARM: 16개**) | 상대적으로 적음 (x86: 8개 범용) |
| **디코더 / 전력** | 회로가 단순하여 <span class="hl-yellow">**저전력·소형화**</span>에 유리 | 디코더가 거대하여 고전력 소비 |
| **대표 아키텍처** | **ARM**, RISC-V, MIPS | Intel x86, x86-64 |

1⇒ 구조 단순 → 트랜지스터 수 적음 → <span class="hl-yellow">저전력</span>, <span class="hl-yellow">소형화</span> 가능 → <span class="hl-yellow">저비용</span>

2⇒ 명령어 길이 고정 → 결정론적 실행 시간 → <span class="hl-yellow">실시간성</span>에 유리

* **C 코드 실행 방식 비교 (`a = b + c;`):**
    * RISC

        ```nasm
        ldr r2, [fp, #-8]     @ r2 = b
        ldr r3, [fp, #-12]    @ r3 = c
        add r3, r2, r3        @ r3 = b + c
        str r3, [fp, #-4]     @ a = r3
        ```

    * CISC

        ```nasm
        mov eax, DWORD PTR [ebp-8]     ; eax = b
        add eax, DWORD PTR [ebp-12]    ; eax += c  (메모리 피연산자 직접 사용)
        mov DWORD PTR [ebp-4], eax     ; a = eax
        ```

### Part 2. ARM 비즈니스 모델 및 Cortex-M4 핵심 특성

#### 1) 저전력 모드

1. **관련**
    1. WFI: Wait For Interrupt, 인터럽트 올 때까지 코어 재움
    2. ISR: Interrupt Service Routine, 인터럽트가 오면 실행되는 처리 함수

2. **STM32 주요 모드**
    1. **sleep**: CPU만 정지, 주변 장치 작동

        ex. CPU가 센서 데이터 기다리는 동안 sleep 상태로 있다가 인터럽트 받자마자 즉시 복귀

    2. **stop**: 모든 클록 정지, SRAM 유지
        * 외부 신호로만 깰 수 있음(클록도 멈춰서)

    3. **standby**: 전원 차단, 일부 레지스터만 유지

        ex. 스마트 미터(원격 전력/가스 검침기)처럼 24시간 내내 자다가 하루에 딱 1번만 깨어나서 센서 값을 서버로 전송하고 다시 잠드는 기기

#### 2) Cortex-M4의 3대 핵심 기술

1. **Thumb-2 ISA (코드 밀도와 성능의 균형):**
    * 순수 ARM(32비트 고정)은 성능 ↑ 코드 크기↑, 초기 Thumb(16비트 고정)은 코드↓ but, 성능 ↓.
    * 16비트와 32비트 명령어를 혼합
        * 자주 쓰는 간단한 명령은 16비트
        * 복잡한 연산은 32비트로 컴파일러가 자동 인코딩
    * 순수 32비트 ARM 대비 **Flash 메모리 절감**, Thumb 대비 **성능 향상**(16비트로 쪼개서 해야 했던 거 32비트로 처리하니까)

2. **DSP (Digital Signal Processing)내장:**
    * **1-cycle MAC (Multiply-Accumulate):** 곱셈과 누적 덧셈을 레지스터 왕복 없이 1사이클 만에 (`MLA`, `SMLAL`)

        <details markdown="1">
        <summary>MAC를 베릴로그로</summary>

        ```verilog
        module mac_unit (
            input wire clk, rst_n,// 클록 신호 및 리셋 신호 (Active Low)
            input wire [15:0] b, x,// 16비트 입력 데이터 (필터 계수 b, 입력 신호 x)
            output wire [31:0] acc_o// 32비트 누적 출력값
        );
            reg [31:0] acc;// 32비트 D-플립플롭 레지스터 다발 생성

            always @(posedge clk) begin
                if (!rst_n)
                    acc <= 32'd0;// 리셋 시 누산기 0으로 초기화
                else
                    acc <= acc + b * x;// 핵심: 곱셈과 누적을 1클록에 동시 처리
            end

            assign acc_o = acc;// 누적된 결과를 외부 출력으로 연결
        endmodule
        ```

        </details>

    * **SIMD (Single Instruction, Multiple Data):**
        * 명령어 1개를 여러 데이터에 동시에 적용
        * 32비트 레지스터 하나 → 16비트 데이터 2개 → 처리량 2배(`SADD16`)
        * 32비트 레지스터 하나 → 8비트 4개 → 처리량 4배(`SADD8, UADD8`)
        * 곱셈2 + 덧셈2 → 명령어1(`SMLAD`)

3. **FPU:**
    * 32비트 부동소수점(`float`) 연산을 전용 하드웨어 연산기(`VFMA`, `VMUL` 등)로 직접 처리하여 소프트웨어 흉내 대비 훨씬 빠름

### Part 3. 레지스터와 해저드

#### 1) 레지스터 구조 (총 16개 범용/특수 레지스터 + xPSR)

* **범용 레지스터 (`R0 ~ R12`):** 총 13개.
    * `R0 ~ R7` (Low 레지스터): 3비트만으로 인코딩할 수 있어서 16비트 Thumb 명령어에서 쉽게 접근 가능.
    * `R8 ~ R12` (High 레지스터).
* <span class="hl-yellow">**특수 목적 레지스터:**</span>
    * <span class="hl-yellow">**`R13 (SP, Stack Pointer)`**</span>**:**
        * 스택의 최상단 주소를 가리킴
        * 분리 구동
            * **MSP**(Main SP)
                * OS 커널, 메인 시스템 코드, ISR(인터럽트 핸들러)이 사용
            * **PSP**(Process SP)
                * 일반 사용자 애플리케이션 코드가 사용하는 전용 스택 포인터(RTOS 태스크)
    * <span class="hl-yellow">**`R14 (LR, Link Register)`**</span>**:** 함수 호출 시 복귀할 주소 저장
    * <span class="hl-yellow">**`R15 (PC, Program Counter)`**</span>**:** 다음에 실행할 명령어 주소를 가리킴
    * <span class="hl-yellow">**`xPSR`**</span> **(통합 Program Status Register):**
        * **APSR (Application PSR):** 조건부 플래그
            * N(음수)
            * Z(0)
            * C(캐리 비트)
            * V(오버플로우 발생했는지)

                → ALU 연산 명령어 실행 직후 결과에 따라 1비트씩 갱신

        * **IPSR (Interrupt PSR):** 현재 실행 중인 예외/인터럽트 번호
        * **EPSR (Execution PSR):** Thumb 상태 비트 등 실행 상태

#### 2) 3단계 파이프라인 (Fetch → Decode → Execute)

* 구성:
    * Fetch: 명령어 가져 오기
        * prefetch: 순차적 코드가 실행될 때 파이프라인이 멈추지 않게 다음 명령어를 미리 fetch해서 버퍼에 보관
    * Decode: 명령어 해석(**레지스터 읽기**)
    * Execute: 연산(EX), 메모리 접근(MEM), 레지스터 기록(WB, **Write Back=결과기록**)
* **원리:** 명령어 처리 단계를 겹쳐서 단위 시간당 처리량(Throughput)을 극대화
* 파이프라인이 이득을 보는 조건
    * 작업이 연속으로 들어오고
    * 단계로 쪼갤 수 있고
    * 단계마다 설비가 따로 있고
    * 단계 시간이 비슷해야
* **CPI (Cycles Per Instruction):** F→D→E 3단계 가정하면 명령어가 N개일 때 총 N+2 사이클 → N 이 커질수록 CPI → 1 (해저드 없다고 하면 매 사이클마다 명령어 1개씩 완료하니까)에 수렴

#### 3) 파이프라인 해저드(Hazard)와 해결 기법

```
[데이터 해저드 해결]
ADD R1, R2, R3 (Execute 단계에서 R1 생성)
      │ (ALU 결과를 Bypass/Forwarding 회로로 직결)
SUB R4, R1, R5 (다음 Execute 단계 입력으로 즉시 전달 ➔ Stall 없음)
```

1. <span class="hl-yellow">**데이터 해저드**</span> **(Data Hazard):** **앞 명령의 연산 결과를 뒤 명령이 즉시 사용**하려 할 때 발생.
    * **ALU → ALU 연산:** <span class="hl-yellow">**Bypass**</span> **(**<span class="hl-yellow">**Forwarding**</span>**)** 회로를 통해 ALU 연산 결과를 **레지스터에 기록하기 전**, 다음 Execute 입력으로 직접 전달 → **Stall 없이 0사이클 지연**으로 처리

        ![Forwarding 없이 Stall이 생기는 경우(5사이클)와 Forwarding 적용으로 Stall이 제거되는 경우(4사이클) 비교](/assets/img/posts/Embedded_3/image.png){: .s70}

    * **`LDR`** **→ ALU 연산 (Load-Use Hazard):** `LDR`은 <span class="hl-yellow">메모리 접근 시간이 필요</span>하므로 Forwarding을 적용해도 1사이클 Stall이 필수 발생(EX → MEM → WB 기준으로 했을 때 LDR 연산은 MEM 접근하고 결과가 나와서 다음 명령어의 EX보다 한 박자 늦음)

        → (컴파일러가 앞 결과랑 상관없는 명령어를 중간에 끼워 넣는 Instruction Scheduling으로 극복)

2. <span class="hl-yellow">**제어 해저드**</span> **(Control Hazard):** 분기 명령어(BEQ 등)가 **Execute 단계에서 조건 판단**하는데 그거 완료하기 전에 다음 명령어를 **미리 Fetch해서** 발생
    * **조건 미발생**(점프 안 함)**:** 미리 인출한 명령을 그대로 실행하여 **1사이클** 소요
    * **조건 발생:** 잘못 미리 인출한 명령어를 버리고(**Flush**), 타깃 주소(점프할 곳)부터 파이프라인을 다시 채움(**Refill**).
    * **Refill 페널티:** 분기가 발생했을 때 파이프라인을 비우고 새 목적지 주소의 명령어로 다시 채우는 데 드는 추가 사이클
        * Cortex-M4 기준 (P(refill에 걸리는 사이클 수)= 1~3) 사이클이며, 총 분기 소요 시간은 (1 + P) 사이클(1은 분기문 자기 자신)
        * 예시
        * 시간 계산 <span class="hl-yellow">1</span>+P(<span class="hl-orange">2</span>)

            | 사이클 | 1 | 2 | 3 | 4 | 5 |
            | --- | --- | --- | --- | --- | --- |
            | B(분기) | F | D | <span class="hl-yellow">E</span> |  |  |
            | 다음 명령1 |  | F | D(버림) |  |  |
            | 그다음 명령2 |  |  | F(버림) |  |  |
            | 목적지 명령 |  |  | F | <span class="hl-orange">D</span> | <span class="hl-orange">E</span> |

++) 분기 명령어

| 명령 | 타겟 주소 위치 | 주소 알 수 있는 시점 | 명령 시간 |
| --- | --- | --- | --- |
| B/BL | 명령어 안에 | decode | 1+P |
| BEQ | 명령어 안에 | decode | 분기O(1+P), X(1) |
| BX Rm | 레지스터에 | Rm 값 준비 되어 있으면 decode, 아니면 될 때까지 stall | 1+P |
| TBB | 메모리 점프 테이블에 | execute에서 메모리 읽은 후에야 | 2+P(테이블 읽기 포함) |

* 타겟 주소가 명령어 안에 있으면 Decode에서 주소 확정 → speculative fetch(추측 fetch) 가능 → refill 페널티(P)↓
* 정렬 여부에 따른 fetch, refill 비용 차이
    1. 정렬 O → fetch word 1번으로 fetch 가능
    2. 정렬 X → fetch word 2번 필요 → refill 완료 시점 지연 → P↑

### Part 4. Harvard 아키텍처와 버스 매트릭스

#### 1) Von Neumann vs Harvard 아키텍처

* **Von Neumann:** 프로그램과 데이터가 **단일 메모리/단일 버스**를 공유 → 명령어 Fetch와 데이터 읽기를 동시에 할 수 X
* **Harvard:** 프로그램 메모리와 데이터 메모리가 분리 → 독립된 버스로 동시 접근 가능
* **Cortex-M4:** 내부는 하버드 구조(독립 버스)이지만, 프로그래머 관점의 외부 주소 공간은 하나로 통합

#### 2) Cortex-M4 3대 버스 및 Bus Matrix

* **I-Code Bus:** Flash 메모리에서 명령어를 Fetch (`0x0000_0000 ~ 0x1FFF_FFFF`)
* **D-Code Bus:** Flash 메모리에서 데이터/상수를 읽음 (`0x0000_0000 ~ 0x1FFF_FFFF`, 별도 경로)
* **System Bus:** SRAM, 주변장치(GPIO, ADC 등)에 접근 (`0x2000_0000` 이상)

⇒ 이 버스들이 도착하는 게 **Bus Matrix:** 여러 마스터가 여러 슬레이브(Flash, SRAM, 주변장치)에 동시에 접근할 수 있도록 중재

### Part 5. 신호처리 하드웨어(DSP/FPU), 병렬성, 타 프로세서 비교

#### 1) 내장 DSP 연산기

* **기본 연산:**
    * **FIR 필터:** ($y(n) = \sum_{k=0}^{N-1} b(k) \cdot x(n-k)$)

        → 곱셈 후 누적(MAC)이 반복되는 구조

#### 2) Single-precision FPU

* C코드는 같은데 컴파일 옵션 바꾸면 → **컴파일러**가 FPU 전용 연산기로 처리하게 함
* **주의사항3:**
    1. `double` 타입 가속X**:** Cortex-M4 FPU는 float(32비트) 전용 ⇒ 실수 상수에 `f`를 붙이지 않거나(1.5f 이런 식으로), `sqrt()`를 쓰면 double로 승격되어 소프트웨어 연산(가속X)
    2. 런타임에 FPU 켜기**:** 안 켜고 `VMUL` 실행 시 `UsageFault`
    3. **ABI** **옵션 일치:**
        * ABI: Application Binary IF, 함수를 부를 때 매개변수를 어느 레지스터에 실어보낼지 정한 약속
        * `mfloat-abi=` 옵션: float 인자 싣는 곳
            * `soft`: 코어 레지스터(FPU 명령도 안 씀)
            * `softfp`: 코어 레지스터로 전달 후 FPU 연산

                → SW는 \_\_aeabi_fmul이 보임

            * `hard`: FPU 레지스터에 직접 전달

                → HW는 VMUL.F32가 보임

#### 3) 프로세서 특성 비교 (MCU vs DSP vs FPGA vs GPU)

| 구분 | MCU (Cortex-M4) | DSP 전용칩 | FPGA | GPU |
| --- | --- | --- | --- | --- |
| **동작 방식** | 명령어 순차 실행 | 명령어 순차 실행 | **회로 물리적 공간 배치** | 스레드 대량 병렬 |
| **특징** | **제어 + 가벼운 신호처리** | 고밀도 MAC 연산 | 회로배선 변경, **1클럭 완전 병렬** | 대량 행렬(ex. 딥러닝 연산) |
| **장점** | **저전력/저비용/쉬운 개발** | 신호처리 특화 | 초저지연, 결정적 타이밍 | 데이터 처리량 多 |

#### 4) 병렬성 (Parallelism) vs 동시성 (Concurrency)

* <span class="hl-yellow">**병렬성**</span> **(Parallelism):** 물리적 자원(멀티코어, GPU, SIMD)이 여러 작업을 **진짜 동시에 실행**
* <span class="hl-yellow">**동시성**</span> **(Concurrency):** 단일 코어에서 **시분할 스케줄링** → 통해 같은 시간 구간 동안 여러 작업이 진행되는 것처럼 보이게 하는 것

    **⇒ Cortex-M4:** 싱글 코어 프로세서 → 병렬성X, 인터럽트+RTOS로 **동시성 구현**

### \[보충\] 동작 모드 (Thread Mode vs Handler Mode)

* **Thread Mode:** 평소 일반 애플리케이션 코드가 실행되는 모드.
* **Handler Mode:** 인터럽트/예외가 발생하면 자동으로 전환되는 모드 (항상 특권 권한인 Privileged 상태로 동작).

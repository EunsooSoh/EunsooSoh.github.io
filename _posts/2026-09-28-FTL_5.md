### 4.3 SSR

* SSR은 hybrid mapping 기반
* 이전 기법들과의 차이: lsn으로부터 lbn을 정하는 hash function을 두 개 제공
    * hash function: lsn을 받아서 logical block number를 결정하는 함수

    | | 식 | 모드 이름 |
    |---|---|---|
    | H1 | lbn = lsn / ns | clustered mode |
    | H2 | lbn = lsn % ns | scattered mode |

    * ns = 한 block 안의 sector 수

    * 이전 FTL 알고리즘들(Mitsubishi, FMAX 등)은 모두 H1 기반

* Fig. 11, clustered mode 동작 예시

    ![Fig. 11](/assets/img/posts/FTL_5/image.png){: width="500" height="312" }
    * 가정: 1 physical block = 4 sector
    * `write(5, A)`:
        * lbn = 5/4 = 1 계산
        * 매핑 테이블로 physical block number 10 획득
        * pbn=10의 offset 0이 비어있으므로 → 첫 sector 위치에 A를 씀
        * logical sector number(5)를 spare area에 기록
    * 이후 write(4,B), (6,C), (7,D)도 같은 방식 (pbn=10의 다음 빈 sector에 차례로, spare area에 각각 4, 6, 7 기록)
    * write(8,E), (9,F), (8,G), (9,H)는 lbn=2 → pbn=11에 차례로 씀 (spare area에 8, 9, 8, 9 기록)
    * SSR에서는 logical sector offset이 physical sector offset과 같을 필요가 없음 → 그래서 lsn을 spare area에 반드시 기록해야 함.

* Read 동작
    * 같은 lsn의 데이터가 block 안에 여러 개 있으면, block의 뒤쪽 끝에서부터 첫 번째로 만나는 sector가 가장 최근 값
    * 예: lsn 9의 유효 데이터는 pbn=11의 네 번째 sector인 H (앞의 F는 옛 값)

* Free sector가 없는 경우
    * physical block에 free sector가 없으면 copy와 erase 연산을 수행

### 4.4 Log block scheme

* 목표: 아래 두 가지 접근 패턴을 모두 효율적으로 처리
    * 긴 sequential write가 많이 발생하는 경우
        * sequential write: logical sector number가 연속해서 증가하는 순서로 데이터를 쓰는 패턴
        * ex. write(4,A), write(5,B)
        * 처음 쓰는 sector들이라 정해진 offset 자리에 그대로 들어가고, 이미 찬 자리에 쓰는 것도 아니니까 erase도 필요X -> block mapping의 고정 offset 규칙과 잘 맞음 
    * random overwrite가 소수 발생하는 경우
        * random overwrite: 이미 데이터가 쓰인 logical sector를 흩어진 순서로 다시 쓰는 패턴
            * ex. write(4,C), write(4,D)

* 구조: physical block을 두 종류로 나눠서 관리
    * data block: 
        * 대부분의 physical block. 
        * block addressing 수준으로 관리. (=주소 매핑을 block단위로만 함)
        * 주로 긴 sequential write에 사용
    * log block: 
        * 작고 고정된 수의 physical block. 
        * sector addressing 수준으로 관리(=주소 매핑을 sector단위로만 함)
        * 주로 random overwrite에 사용
        * log block들은 pool로 관리

* 주소 매핑: RAM에 두 종류의 매핑 테이블을 유지
    * data block용 block mapping table
    * log block용 sector mapping table

* 동작 방식
    * 어떤 sector가 data block에 처음 쓰인 뒤 같은 logical sector에 overwrite가 오면, log block pool에서 할당된 log block으로 보냄
    * 같은 logical sector에 대한 이후의 overwrite도 모두 그 log block에서 처리(Fig 12처럼 log block free sector에 그 데이터를 쓰고, log block의 spare area에 lsn 기록)
    * log block에 free sector가 없으면 log block의 데이터를 대응하는 data block에 merge하고, log block은 pool로 반환해서 이후 overwrite에 재사용
        * overwrite에 쓸 free log block이 없으면
            1. 사용 중인 log block 중 victim log block을 선택
            2. victim log block의 데이터를 대응하는 data block과 merge
            3. victim log block을 erase
            4. erase된 block을 현재 overwrite에 할당

* Fig. 12, Log block scheme 동작 예시

    ![Fig. 12](/assets/img/posts/FTL_5/image-2.png){: width="700" height="460" }
    * 가정: 1 physical block = 4 sector
    * write 순서: (4,A), (5,B), (4,C), (4,D), (8,E), (9,F), (8,G), (9,H)
    * `write(4, A)`:
        * lbn = 4/4 = 1, logical page offset = 4%4 = 0 계산
        * block-level 매핑 테이블로 physical block number 10 획득
        * pbn=10의 offset 0이 비어있으므로 → 첫 sector 위치에 A를 씀
    * `write(4, C)` (lsn 4에 대한 두 번째 write):
        * pbn=10의 offset 0은 이미 점유됨 → log block(pbn=20)에 씀
        * log block에서는 logical sector offset이 physical sector offset과 같을 필요가 없음 → psn만으로 lsn 모르니까 lsn을 spare area에 기록
    * 이후 write도 같은 방식으로 처리
    * 최종 상태
        * data block: pbn=10에 A, B / pbn=11에 E, F
        * log block: pbn=20에 C, D (spare area: 4, 4) / pbn=30에 G, H (spare area: 8, 9)
        * block-level 매핑 테이블: lbn 0 → pbn 5, lbn 1 → pbn 10, lbn 2 → pbn 11
        * log block용 sector-level 매핑 테이블: (lbn 1, pbn 20, lsns {4,4}), (lbn 2, pbn 30, lsns {8,9})

* 매핑 정보 저장 방식
    * map block method 사용
    * **data block용** block mapping table은 **map block** 중 하나에 저장
    * map block pool에서 block mapping table의 최신 버전을 찾기 위해 RAM에 map directory를 유지
        
        ++) 추가(외부 문서: Kim et al., IEEE TCE 2002)
        * map directory: 매핑 테이블이 flash의 map block에 조각 단위로 저장되는데, 그 조각들이 map block 어디에 있는지 알려주는 정보 (RAM/SRAM에 유지)
        * 시작 시 마지막으로 쓴 map block부터 역순으로 스캔해서 map directory를 구성
            -> 각 매핑 테이블 조각들의 최신 위치를 알 수 있음
    * power-off 복구를 위해 **log block용** sector mapping table이 갱신될 때마다 map directory를 flash의 **checkpoint block**에도 저장
        * checkpoint block은 그냥 map directory를 flash에 백업해 두는 특정 block

* 변형 기법
    * FAST: 하나의 physical block(log block)에 둘 이상의 logical block을 매핑할 수 있어서 log block의 공간 활용도가 높아짐
        
        ++) 추가(외부 문서)
        * 쓰는 이유: log block은 수가 적고 고정되어 있음. 근데 logical block마다 하나씩 배정해주니까 금방 바닥남 -> merge 빈번해질 수 있음
        * log block을 여러 logical block이 나눠 쓰게 함.
    * STAFF: block에 state를 부여하고 이를 address mapping 제어에 사용해서 erase 연산을 최소화

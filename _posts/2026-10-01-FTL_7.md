### log block이 필요한 이유

* 플래시 메모리는 덮어쓰기가 안 됨 
* -> 이미 쓴 페이지를 고치려면 블록 전체를 erase해야 하는데, erase 연산이 느림. 
* -> 그래서
    1. 수정된 데이터를 일단 다른 빈 곳에 적어두고, -> 여기서 빈 곳이 log block
    2. 나중에 몰아서 정리하는 방식을 씀. -> 원본 데이터 블록과 합쳐서 정리하는 게 merge
        * merge 연산 안에도 erase가 여러 번 있어서 merge 횟수를 줄이는 게 성능에 도움

### BAST

* Fig 2. merge_vs_switch

    ![Fig 2](/assets/img/posts/FTL_7/BAST_Fig2_merge_vs_switch.png){: .s70 }
    
* Block-Associative Sector Translation
* 논리 블록 하나에 log block 하나를 전용으로 붙임
    * 블록 0의 수정은 블록 0 전용 log block에만, 블록 1의 수정은 블록 1 전용 log block에만

* 장점: 
    * 단순함
    * merge할 때 log block 하나에 한 논리 블록 데이터만 있으니 merge도 한 번이면 끝
    * 순차 쓰기면 log block을 그대로 데이터 블록으로 바꿔치기하는 저렴한 **switch** 연산도 가능.
        * 데이터 블록은 논리 위치가 고정이지만 log block은 고정이 아님(온 순서대로 채워짐)
        -> 그래서 데이터가 순차적으로 들어오면 lsn = psn이라서 log block 다 차면 그냥 통째로 switch하면 됨((1) 이 log block을 데이터 블록으로 매핑 정보 변경 (2) 옛날 데이터 블록을 erase)

* 단점
    1. 블록 스래싱(thrashing).
        * 논리 블록 하나 당 log block 하나만 주기 때문에 log block 수가 적으면 매번 log block을 빼앗고 merge해야 함. -> 그 시점에 활성 상태인(=아직 merge 안 된)논리 블록 수보다 log block 수가 적으면 merge 횟수 증가

    2. 공간 낭비
        * 한 블록만 집중적으로 고치는 경우, 전용 log block이 금방 차서 merge가 발생. 
        * 다른 log block이 텅 비어 있어도 "남의 것"이라 못 씀. 
        => 낮은 space utilization이 BAST의 핵심 문제

### FAST

![Fig 3.](/assets/img/posts/FTL_7/FAST_Fig3_cache_analogy.png){: .s70 }

* Fully-Associative Sector Translation
* 어떤 섹터든 아무 log block에나 쓸 수 있게 함
* 이렇게 하면 BAST의 두 문제가 해결
    * 빈 칸을 남김없이 쓰니 merge 횟수 자체가 줄어듭니다
    * 한 블록을 집중적으로 고치는 경우도 log block 두 개면 충분해서 BAST에서 피할 수 없던 merge를 피하거나 늦출 수 있음

* but, 모든 쓰기를 섞어 쓰면 switch 같은 저렴한 연산을 할 기회X 
    -> FAST는 log block2
        - **SW log block 1개**: 순차 쓰기 전용 (switch 최적화 유지)
        - **RW log block 여러 개**: 랜덤 쓰기를 공용으로 받음

### FAST의 대가
아무 데나 섞어쓴 것의 단점

* 한 RW log block 안에 여러 논리 블록의 섹터가 섞여 있으니, 그 log block을 정리할 때 **섞여 있는 논리 블록 수만큼 merge를 해야** 함(BAST는 항상 1번).
    * 로그블럭 1에 A(lbn=1), B(lbn=2), C(lbn=1), D(lbn=2) 이렇게 되어 있으면 lbn=1에 대응 되는 데이터 블록으로 가서 거기서 valid한 데이터+로그블럭에 있는 데이터 모아서 새로운 블럭으로 옮기면서 invalid로 바꾸고 원래 데이터 블록과 log block erase, lbn=2에 대응되는 것도 마찬가지
* 최신 데이터 찾으려면 log block을 섹터 단위 매핑 테이블로 뒤져야 해서 읽기에 약간의 오버헤드가 생김(SRAM 테이블 스캔이라 크진 않음).

그럼에도 merge 발생 빈도 자체가 크게 줄어서, 논문은 최선의 경우 전체 수행 시간과 erase 횟수를 각각 50% 이상 줄였다고 함.

### 한눈에 비교

| | BAST | FAST |
|---|---|---|
| 매핑 방식 | 논리 블록 ↔ log block 1:1 전용 | 아무 섹터나 아무 log block에 |
| 캐시 비유 | Direct-mapped | Fully associative |
| 로그 공간 활용도 | 낮음 | 높음 (빈 칸 끝까지 사용) |
| merge 빈도 | 잦음 (스래싱 발생) | 적음 |
| merge 1회당 비용 | 싸다 (논리 블록 1개) | 비쌀 수 있다 (논리 블록 여러 개) |
| 순차 쓰기 | switch 가능 | 전용 SW log block으로 switch 유지 |

### 한 줄 요약

> **BAST는 단순하지만 낭비가 많고,
> **FAST는 낭비 없이 꽉 채워 쓰는 대신 정리할 때 비용 더 큼

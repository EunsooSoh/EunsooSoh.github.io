- 임계구역 동기화 문제를 해결하기 위한 조건3
    - mutual exclusion: 어떤 프로세스가 자신의 임계구역 내에서 코드를 실행 중일 때, 다른 어떠한 프로세스도 자신의 임계구역에 진입 불가
    - progress: 현재 임계구역에서 코드를 실행하고 있는 프로세스가 없으면, 진입을 기다리는 프로세스가 무한정 기다릴 수 없음 ⇒ 데드락 예방
    - bounded waiting: 진입까지 기다리는 데에 한계가 있음 ⇒ 기아 예방

### 고전적 동기화 문제

1. **Bounded Buffer(생상자-소비자 문제)**
    - 공유자원: count, in, out, buffer
    - 해결: counting semaphore
        - **`mutex`**: 버퍼 접근을 통제 → 초기값 1이고 P, C 모두 wait
        - **`empty`**: 남은 칸 수 → 초기값 N → P가 wait
        - **`full`** : 채워진 칸 수 → 초기값 0 → C가 wait
            - C는 버퍼가 비었으면 wait
            - P는 버퍼가 가득 차 있으면 wait
    - 위험 요소 (Deadlock): mutex 잡고 잠들어서 발생
        
        ⇒ 잠들 수 있는 wait(ex. 자원 확인)는 **`mutex`**를 잡기 전에 해야 함
        
        - 문제코드
        
        ```c
        wait(mutex); // (BAD) lock 1st
        wait(empty); // mutex를 잡고 SLEEP 
        ```
        
        자원 세마포어(**`empty`**나 **`full`**)를 기다리는 **`wait()`** 연산을 **`mutex`**로 잠근 임계구역 내부에서 호출하면, 잠든 스레드가 **`mutex`**를 쥐고 있어 반대편 스레드도 진입하지 못하는 데드락이 발생
        
        - 해결 코드 (조금 말만 다를 뿐 CV에서는 not full을 기다리는 거, 여기는 empty가 생길 때까지 기다림)
        
        ```c
        while (true) {
            item x = produce ();
        
            wait(empty); // (1) empty가 생길 때까지 기다려라
            wait(mutex); // (2) lock buffer
        
            buffer[in] = x;
            in = (in + 1) % N;
            count ++;
        
            signal(mutex); // (3) unlock
            signal(full); // (4) item ready
        }
        ```
        
2. **Readers-Writers Problem**
    - 공유자원: read_count, writer_lock(rw_mutex)
    - 다수의 Reader는 동시 접근을 허용하고, Writer는 배타적 접근을 보장해야. (읽기 비중이 큰 경우에 시스템에 적용됨)
    - 해결:
        - **`read_count`**: 읽는 스레드 수 → 초기값 0
        - **`rw_mutex`**: 공유 자원에 대한 lock → 초기값 1
            - reader: 누가 쓰고 있으면 lock 획득 못함. 첫 번째 reader가 lock 얻으면 이후에 오는 reader들은 그냥 다 읽음. (→ read_count 0될 때까지 writer가 못 들어가는 기아 상태에 빠질 수 있음)
            - writer: 누가 읽고 있거나 누가 쓰고 있으면 lock 획득 못함
        - **`mutex`**: read_count만 보호하기 위한 lock → 초기값 1, 모든 reader가 대기
        
        ```c
        // Reader
        wait(mutex); // read_count 보호용 Mutex
        read_count++;
        if (read_count == 1) wait(rw_mutex); // 첫 번째 Reader가 Writer 진입을 막음
        // 1. reader 하나가 처음 들어오면 read_count = 1됨
        // 2. if에 걸려서 rw_mutex를 얻기를 기다림.
        // 3. 그래서 그거 잡으면 writer는 rw_mutex 기다리니까 진입 못함
        signal(mutex);
        
        read(shared_data); // 다수의 Reader 병렬 실행 구간
        
        wait(mutex);
        read_count--;
        if (read_count == 0) signal(rw_mutex); // 마지막 Reader가 빠져나갈 때 Writer 진입 허용
        signal(mutex);
        ```
        
        ```c
        // Writer
        wait(rw_mutex); // Writer는 혼자만 독점
        write(shared_data);
        signal(rw_mutex);
        ```
        
    - **위험 요소 (Starvation)**: 정책(Policy) 설계에 따라 기아 상태가 발생할 수 있음. Reader를 우선하면 Writer가 영원히 대기하는 Writer Starvation이, Writer를 우선하면 Reader Starvation이 발생할 수 있으므로 공정성 절충이 필요
    - reader가 mutex를 쥔 상태로 rw_mutex를 기다리며 잠들 수 있지만, writer는 mutex를 원하지 않으므로 데드락은 발생하지 않음.
3. **Dining Philosophers (식사하는 철학자들)**
    - 공유 자원: fork lock 배열(원소 N개, 코드에서 lock_t forks 생략)
    - **위험 요소 (Circular Wait)**: 모든 철학자가 왼쪽 포크를 집고 오른쪽 포크를 기다리면 원형 대기(Circular Wait)가 형성되어 데드락.
    - 해결:
        - **lock ordering**: 자원 전체에 전역적인 번호를 매기고, 자원 순서 강제 → Circular wait 파괴(사이클이 안 생겨서)
            - 간단한 예시 - 항상 번호가 낮은 lock부터 획득하게
                
                ```c
                // Thread 1
                lock(&L1);
                lock(&L2);
                // critical section
                unlock(&L2);
                unlock(&L1);
                
                // Thread 2: same order
                lock(&L1);
                lock(&L2);
                // critical section
                unlock(&L2);
                unlock(&L1);
                ```
                
            
            ![환형 대기(circular wait) 예시: 위는 R1→T1→R2→T2...가 순환해 데드락 발생, 아래는 T4가 1,4 순서로 자원을 요청해 T2/T4는 기다리지 않아 데드락이 아닌 경우](/assets/img/posts/OS_6/image.png){: width="532" height="700" }
            
            T4가 1, 4(오름차순) 순서로 자원을 요청함. 아마 R1을 얻기 위해 T1과 경쟁했으나 T1이 자원을 획득했을 것. 그래서 T4는 아무것도 hold하지 않고 R1을 wait하고 있음
            
        - 동시 진입 제한: 최대 N-1(공유 자원 수보다 적게)개의 스레드만 fork 경쟁에 참여 → Circular wait 파괴(사이클이 안 생김)
        - 양쪽 포크가 다 사용 가능할 때만 집기 → Hold and Wait 파괴
        - waiter(중앙관리자 두기) → Hold and Wait 파괴
        - Try-lock: 자원 획득(여기서는 fork 락) 실패하면 내려놓고 재시도 → 비선점 파괴(hold and wait 파괴라고도 볼 수 있음)
            
            but, livelock 위험 (해결 방안!)
            
            1. 다 같이 왼쪽 포크를 집음
            2. 다 같이 오른쪽 포크에 try-lock → 모두 실패
            3. 다 같이 내려 놓음
            4. 또 다 같이 왼쪽 포크 … again ⇒ 재시도 전 대기 시간을 무작위로 하든지 우선순위 줘서 일부가 먼저 하게 하든지

### 동기화 버그

- Liveness(시스템 진행률) 문제 3(**멈춤의 종류**)
    - **Deadlock (교착 상태)**: **자원 순환 대기로 모두 sleep**, CPU 사용X
    - **Livelock**: 각 스레드가 계속해서 상태를 변경(running)하며 움직이지만(CPU 100% 사용), 실제 의미 있는 진행은 없음 (예: 계속된 **`try-lock`** 실패 후 동시 재시도).
    - **Starvation (기아 상태)**: 시스템 전체는 정상 진행되지만, 특정 스레드만 자원을 받지 못해 무한히 밀리는 상태.
- **Non-Deadlock Bugs**
    - 원자성 위반**(Atomicity Violation 중 하나인 TOCTOU)**
        - time of check to time of use
        
        : 상태를 확인(Check)하는 시점과 사용하는 시점(Use) 사이에 다른 스레드가 개입하여 상태를 바꾸는 버그
        (예: if(ptr) { use(ptr); }사이의 개입). 
        
        ⇒ check와 use 구간 전체를 같은 락으로 묶어야 해결
        
        - 해결 예시
            
            setuid 파일 검사는 내부 스레드끼리가 아니라서 그냥 열고 그 안에서 검사해서 사용 추천 
            
            ```c
            lock(& proc_lock);
            if (thd ->proc_info) {
                fputs(thd ->proc_info , ...);
            }
            unlock (& proc_lock);
            ```
            
    - **순서 위반 (Order Violation)**: 스레드 간의 실행 순서가 지켜지지 않아 발생
        
        ⇒ 조건 변수(CV)나 세마포어를 통해 순서를 강제하여 해결
        
        - 예시 코드
            
            ```c
            // Thread 1 (Main)
            void init() {
                // 스레드 생성 및 mThread 할당
                mThread = createThread(mMain); 
                
                // 2. 할당이 끝났음을 알리기 위해 락을 잡고 상태 변경 후 시그널 전송
                pthread_mutex_lock(&m);
                is_initialized = true;       // 초기화 완료 표시
                pthread_cond_signal(&cv);    // 자고 있는 자식 스레드를 깨움
                pthread_mutex_unlock(&m);
            }
            
            // Thread 2 (Child)
            void mMain (...) {
                // 3. mThread를 사용하기 전에 초기화가 완료되었는지 확인
                pthread_mutex_lock(&m);
                while (!is_initialized) {
                    // 초기화가 안 되었다면 락을 풀고 조건 큐(cv)에서 대기
                    pthread_cond_wait(&cv, &m); 
                }
                pthread_mutex_unlock(&m);
                
                // 4. 이 시점에서는 mThread가 100% 할당되어 있음이 보장됨! 안전하게 접근 가능
                state = mThread->state; 
            }
            ```
            
1. **데드락**
    - 조건
        
        아래 네 조건을 만족하면 데드락이 발생할 수 있음(데드락 → 조건4. 즉 조건 하나라도 만족 안 하면 데드락 아님). 여기서 말하는 자원은 락임.
        
        - 데드락 발생 예시(락 잡는 순서 교차)
            
            ```c
            // Thread 1
            lock(&L1);
            lock(&L2);
            // critical section
            unlock (&L2);
            unlock (&L1);
            
            // Thread 2: different order
            lock(&L2);
            lock(&L1);
            // critical section
            unlock (&L1);
            unlock (&L2);
            ```
            
        1. **상호배제 (Mutual Exclusion)**: 한순간에 하나의 스레드만 자원 점유 가능. (공유 가능한 건 대기 자체를 안 하니까 데드락X)
        2. **점유대기 (Hold and Wait)**: 자원을 이미 가진 상태에서 다른 자원을 대기.
        3. **비선점 (No Preemption)**: 남이 쥔 자원을 강제로 뺏을 수 없음.
        4. **원형대기 (Circular Wait)**: 대기 관계가 닫힌 사이클을 이룸.
    - Resorce Allocation Graph
        - 자원이 1instance일 때 사이클 생기면 무조건 데드락
            
            → RAG로 Avoidance할 수 있음(요청, 할당 간선말고 미래에 요청할 수 있다는 의미인 claim 간선까지 그렸을 때도 사이클 안 생길 때만 할당)
            
            cf. 자원이 여러 인스턴스를 가지면 사이클이 생겨도 데드락 아닐 수 있음
            
            ![자원이 여러 인스턴스일 때 사이클이 생겨도 데드락이 아닐 수 있는 예시: T2/T4는 아무것도 기다리지 않아 끝나면 자원을 반납해 cycle이 해소됨](/assets/img/posts/OS_6/image-1.png){: width="700" height="364" }
            

### 대응 전략5

1. **Prevention (예방)**: 발생 전 4조건 중 하나 차단. 
    
    ex. Lock Ordering을 통해 원형 대기를 파괴.
    
    (1) Mutual Exclusion 깨기—공유 가능하게(read only에서)
    
    ```c
    // read-only 데이터는 lock 자체가불필요
    const Config* cfg = load_once ();
    read(cfg ->value); // 누가봐도 OK
    
    // 또는 lock -free (CAS 기반)
    do {
        old = *p;
        new = old + 1;
    } while (!CAS(p, old , new)); // 내가 읽었던 값이 그대로일 때만 갱신
    ```
    
    (2) Hold-and-Wait 깨기—한꺼번에 OR 빈손에서만
    
    ```c
    // (a) 일괄획득 (atomic)
    if (! try_lock_all(L1, L2, L3)) {
        /* 한번에 다 못 잡으면 전부 포기 */
        return RETRY;
    }
    // (b) 빈손에서만 요청
    release_all ();
    acquire(L1);
    acquire(L2); // 빈손 보장
    ```
    
    (3) No Preemption 깨기—강제 회수 → livelock 위험으로 random backoff 필수
    
    ```c
    // try_lock 실패시보유 lock 모두 반납
    acquire(L1);
    if (! try_lock(L2)) {
        release(L1); // 양보!
        backoff ();
        goto retry;
    }
    ```
    
    (4) Circular Wait 깨기 - 전역 순서
    
    ```c
    // 모든가 thread lock id 오름차순으로획득
    if (L_a.id < L_b.id) {
        acquire(L_a);
        acquire(L_b);
    } else {
        acquire(L_b);
        acquire(L_a);
    }
    ```
    
2. **Avoidance (회피 - Banker's Algorithm)**: 각 스레드가 사용할 최대 자원량(Max)을 사전 선언, 요청을 수락했을 때 시스템이 'Safe State(모두 무사히 끝마칠 수 있는 상태)'를 유지할 때만 자원을 내어줌. 
    - Max 사전 선언이 비현실적
        - Need = Max - Allocation
    - 매 요청마다 $*O(m×n^2)*$의 비용.
    - safe state: 모든 스레드의 안전 실행 순서가 존재(cf. unsafe: 데드락 발생 ‘가능’, 무조건은 아님. Max까지 요구하면 안 끝난다)
        - requeset가 아닌 max 값을 이용하는 이유: 최악의 상황을 가정하더라도 safe state가 있는지 보수적으로 확인하기 위해
    - Flow chart ** 문풀 방법: need, allocation 표에서 판단 흐름 다 숫자로 표시해두고, safe path는 그냥 넘버링한 거 오름차순 정렬만
        
        ![Banker's Algorithm 진행 흐름도: 자원 요청 → Need/Available 검사 → 가상 할당 → Safety Algorithm으로 안전한지 판단해 실제 할당 또는 롤백](/assets/img/posts/OS_6/99e7ea43-0bad-4628-bd1e-0194366f27c6.png){: width="700" height="359" }
        
        ```c
        Work = Available
        Finish[i] = false for all i // detection은 여기서 (allocation[i] == 0)인 걸로 하는 것 빼고 걍 need 대신 request 넣으면 똑같음
        
        repeat
        		// 끝나지 않은 것 중 사용가능량 밑으로 요구할 수 있는 거 찾기
            find i such that Finish[i]== false AND Need[i] <= Work
            if no such i: break
            Work = Work + Allocation[i] // 얘는 어차피 내가 줄 수 있는 한도에서 해결가능하니까 해결했다고 치고 할당했던 자원 돌려받음
            Finish[i]= true
        
        if Finish[i]== true for all i: state is SAFE // 이렇게 모든 스레드애 대해서 종료했으면 safe
        ```
        
3. **Detection (탐지)**: 이미 발생한 데드락을 사후에 찾음. 
    - 주기적으로 $*O(m×n^2)*$의 비용.
    - Avoidance와 가장 큰 차이는 Max 필요여부(이건 필요X)
    
    ![데드락 탐지(Detection) 알고리즘 흐름도: Work=Available에서 시작해 Request[i]<=Work인 스레드를 찾아 완료 처리하고, 더 찾을 수 없을 때 남은 스레드를 deadlock 집합으로 판정](/assets/img/posts/OS_6/image-2.png){: width="700" height="304" }
    
    - 1-instance 환경: Wait-for graph의 사이클을 찾기
    - Multi-instance 환경: Request 행렬을 이용해 가상 완료 시뮬레이션을 돌려 탐지.
        
        ```c
        Work = Available
        Finish[i] = (Allocation[i]==0) // 빈손은 OK(빈손 = hold 안 함. 데드락 원인 아님)
        
        repeat
        		// 아직 안 끝났고, 자원 할당해서 끝낼 수 있는 거 찾기(이게 있는 동안 계속 반복)
            find i: Finish[i]== false AND Request[i] <= Work
            if none: break
            // 찾았으면 끝냈다고 가정하고 할당했던 거 회수
            Work += Allocation[i]
            Finish[i] = true // 끝
        
        if any Finish[i]== false:
            DEADLOCK (T_i 들이묶여있음) // 끝낼 수 없는 스레드
        ```
        
4. **Recovery (복구)**
    - 프로세스 종료
        - 일괄 종료
        - 사이클 깨질 때까지 하나씩 종료
    - 자원 선점
        - Victim 선택해서 자원 강제 회수하고 다른 스레드에게 넘김
5. **Ignore (무시)**: 
    - 탐지 후 희생자를 골라 프로세스를 죽이거나 롤백(DB 환경).
    - 범용 OS(Linux/Windows)는 데드락 탐지 비용이 더 크다고 판단하여 무시하며 사용자에게 책임(사용자가 직접 kill).

### **우선순위 역전 (Priority Inversion)**

- 높은 우선순위 스레드(High)가 낮은 우선순위 스레드(Low)가 쥐고 있는 Lock을 기다리며 Block(high: waiting) 되는데, 갑자기 중간 우선순위 스레드(Mid)가 CPU를 선점(high: waiting, low: ready)해버려 Low 스레드가 Lock을 해제하지 못하고, 결과적으로 High 스레드가 무기한 지연되는 현상. 즉, 자원 자체는 풀려 있는데 스케줄링 우선순위와 lock 보유 관계가 어긋남.
    
    ⇒ 
    
    1. **Priority Inheritance (우선순위 상속)**: High 스레드가 Lock에서 막히는 순간, Lock을 쥐고 있는 Low 스레드의 우선순위를 High 수준으로 일시적으로 끌어올려 빨리 Lock을 반납
        
        (내가 기다리는 애의 우선순위를 나만큼으로 올림=내 우선순위를 물려줌)
        
    2. **Priority Ceiling Protocol**: 자원마다 접근 가능한 최고 우선순위를 미리 정해두고, Lock을 잡는 즉시 스레드의 우선순위를 그 천장(Ceiling)만큼 올림

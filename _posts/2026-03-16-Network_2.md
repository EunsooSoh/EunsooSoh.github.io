1. **네트워크 애플리케이션 구조 및 프로세스:** 
    - 네트워크 애플리케이션은 네트워크 코어 장비용 소프트웨어를 작성할 필요 없이 엔드 시스템(종단 시스템)에서 작동
    - 클라이언트-서버 패러다임: 항상 켜져 있는 서버와 동적 IP를 가지는 클라이언트로 구성 ⇒ 클라이언트끼리 통신하지 않음
    - P2P(Peer-to-Peer) 패러다임: 항상 켜져 있는 서버 없이 피어(Peer) 간 직접 통신하여 자가 확장성을 가짐
    - 서로 다른 호스트 간의 프로세스는 메시지 교환을 통해 통신, 소켓(Socket)이라는 인터페이스를 통해 애플리케이션 계층과 트랜스포트 계층 간에 데이터를 주고받음. 소켓은 IP 주소와 포트 번호(예: HTTP 80, Mail 25)로 식별
- **애플리케이션별 트랜스포트 요구사항:** 파일 전송은 데이터 손실(Loss)을 전혀 허용하지 않지만, 오디오/비디오 스트리밍은 손실을 어느 정도 허용(Loss-tolerant). 대역폭 측면에서 웹/이메일은 탄력적(Elastic)이지만, 실시간 멀티미디어는 최소한의 대역폭 보장을 요구
- **웹과 HTTP:** HTTP는 웹의 애플리케이션 계층 프로토콜로, 클라이언트(브라우저)와 서버(웹 서버) 모델 기반이며 TCP를 사용. 서버가 클라이언트의 과거 요청 정보를 저장하지 않는 무상태(Stateless) 프로토콜
    - 전송 후 연결을 끊는 비지속(Non-persistent) 연결 →객체당 2RTT(Round Trip Time) = RTT(handshaking) + RTT(file 요청, 응답) (+file 전송시간)
    - 하나의 TCP 연결로 여러 객체를 전송하는 지속(Persistent, HTTP/1.1) 연결→첫 번째 객체 이후에는 객체당 1RTT(Round Trip Time) = ~~RTT(handshaking)~~ + RTT(file 요청, 응답) (+file 전송시간)
- **HTTP 메시지와 쿠키(Cookie):** HTTP 요청 메시지는 요청 줄(GET, POST, HEAD, PUT)과 헤더 줄로 구성, 응답 메시지는 상태 코드(200 OK, 301, 400, 404, 505 등)와 응답 데이터로 구성. HTTP의 무상태성을 보완하기 위해 쿠키를 사용하여 장바구니, 사용자 세션, 추천 등 멀티 스텝 트랜잭션의 상태를 유지하지만 사생활 침해(추적 쿠키) 우려 존재
- **웹 캐시(프록시 서버):** 클라이언트의 요청을 원본 서버 대신 처리하여 응답 시간을 단축하고 액세스 링크의 트래픽을 감소. 브라우저 캐시에 있는 객체가 최신인지 확인하기 위해 조건부 GET(`If-modified-since`)을 사용, 캐시된 이후 데이터가 수정되지 않았을 경우 객체 데이터 없이 `304 Not Modified` 상태 코드만 포함된 응답을 보내 전송 지연을 방지
- **HTTP/2:** HTTP/1.1에서 발생하는 패킷 대기 지연인 FCFS(들어온 순서) 기반의 HOL(Head-of-line) 블로킹 문제를 해결하여 여러 객체 요청 시의 지연을 감소
    
    ⇒ 전송할 객체들을 더 작은 단위인 '프레임(frame)'으로 쪼개고, 여러 객체의 프레임들을 교차로 섞어서(interleaved) 전송하는 방식
    
- HTTP/3: 그냥 TCP가 해줬던 것들을 application layer에서 만들어 씀
- **이메일(SMTP):** 이메일은 사용자 에이전트, 메일 서버, SMTP 등 세 가지 요소로 구성. SMTP는 클라이언트에서 서버로 메시지를 안정적으로 전송하기 위해 TCP를 사용하는 프로토콜로, ASCII 텍스트 명령과 상태 코드를 통한 응답 방식을 취함. 메일의 구조는 RFC 2822 형식을 따르며 To, From, Subject 등의 헤더를 포함
    - 이메일 시나리오
        
        **[이메일 전송 및 수신 6단계 시나리오]**
        
        1. **메시지 작성:** Alice가 자신의 사용자 에이전트(UA, 예: Outlook, 메일 앱 등)를 사용하여 수신자인 Bob(bob@someschool.edu)에게 보낼 이메일 메시지를 작성
        2. **Alice의 메일 서버로 전송:** Alice의 사용자 에이전트는 **SMTP 프로토콜**을 사용하여 이 메시지를 Alice 측의 메일 서버로 전송, 이 메시지는 서버의 **나가는 메시지 큐(Outgoing message queue)** 에 저장되어 전송을 대기
        3. **TCP 연결 설정:** Alice의 메일 서버 내에 있는 SMTP 클라이언트 측에서 인터넷을 거쳐 Bob의 메일 서버를 향해 **TCP 연결을 오픈(open)**
        4. **인터넷을 통한 메시지 전송:** 설정된 TCP 연결을 통해 SMTP 클라이언트가 Alice의 메시지를 Bob의 메일 서버로 전달
        5. **Bob의 메일 서버 수신:** Bob의 메일 서버는 수신한 메시지를 확인, 이를 **Bob의 개별 메일박스(Mailbox)** 에 안전하게 보관
        6. **메시지 읽기:** 이후 Bob이 자신의 사용자 에이전트를 실행하여 메일 서버에 접속한 뒤, 도착해 있는 메시지를 읽어옴
        
        **[핵심 포인트: 프로토콜의 역할 분리]** 이 시나리오에서 가장 중요한 특징 중 하나는 메일을 **전송(Delivery)할 때와 수신(Retrieval)할 때 사용하는 프로토콜이 엄격히 분리되어 있다**는 점
        
        - **보낼 때 (SMTP):** Alice가 자신의 메일 서버로 메시지를 **밀어 넣거나(Push)**, Alice의 메일 서버가 Bob의 메일 서버로 메시지를 전달하는 과정은 모두 **SMTP**가 담당
        - **받을 때 (메일 액세스 프로토콜):** 6단계에서 Bob이 자신의 메일 서버에 보관된 메시지를 자신의 기기로 **가져올 때(Pull)** 는 SMTP를 쓰지 않고, **IMAP이나 HTTP(웹 기반 이메일의 경우)**와 같은 별도의 메일 액세스 프로토콜을 사용

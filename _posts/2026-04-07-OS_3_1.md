1. waitpid
    
    cf. wait: 임의의 자식, 항상 블로킹
    
    waitpid(pid, &status, options)
    
    ```c
    // 시그널 핸들러 함수
    void chld_handler(int sig) {
        int status;
        pid_t pid;
        
        // WNOHANG 옵션을 주어 멈추지 않고 비동기 수거
        pid = waitpid(-1, &status, WNOHANG);
        if (pid > 0)
            printf("child %d done\n", pid);
    }
    
    int main(void) {
        signal(SIGCHLD, chld_handler); // 자식이 죽으면 chld_handler 호출하도록 등록
        
        pid_t pid = fork();
        if (pid == 0) { /* 자식 프로세스 */
            printf("child: exiting\n");
            exit(42);
        }
        
        sleep(2); /* 부모는 본인 할 일 수행 (블로킹 되지 않음) */
        return 0;
    }
    ```
    
    → 특정 자식의 종료 기다리기, 논블로킹(option: WNOHANG)으로 상태 확인하기
    
    → WNOHANG: 자식 상태를 한 번 확인하고 running이면 바로 나와서 0 리턴
    
    ```c
    pid_t pid = fork();
    
    if (pid == 0) {
        sleep(10);
        exit(0); // 자식: 긴 작업 수행 후 종료
    } else {
        while (1) {
            // WNOHANG 옵션: 자식이 안 끝났어도 멈추지 않고 0을 반환하며 즉시 복귀
            pid_t w = waitpid(pid, NULL, WNOHANG);
            
            if (w == 0) {
                printf("아직 작업중 ...\n");
                do_other_important_work(); // 부모의 다른 작업 계속 수행
                sleep(1);
            } else if (w > 0) {
                printf("자식 종료! 수거완료 .\n");
                break;
            }
        }
    }
    ```
    
    - 보통 BG에서
        
        부모가 waitpid(pid, &status, WNOHANG)
        
        → 자식 종료를 비동기(SIGCHLD)로 알리고
        
        → 핸들러가 논블로킹으로 수거(핸들러 내부에서는 signal로 처리)
        
    
    ++ 자식에서 wait() → -1리턴
    
2. LDE
    
    : 제한된 직접 실행
    
    (1) 위험한 연산에는 OS 개입
    
    (2) OS는 최소 개입
    
    (3) 프로그램을 CPU에서 직접 실행
    
    - 직접 실행과의 비교
        
        → (문1) 사용자가 특권 연산 직접 실행 가능 (문2) CPU 회수가 어려움(ex. 무한 루프)
        
    - 문1 해결: 이중모드와 Trap
        
        특권 연산 필요할 때 Trap으로 커널 진입하게 함
        
        - Trap 메커니즘
            
            ① 트랩 테이블(IDT) 초기화(부팅 시 OS가 특권 명령어로 IDT 설정)
            
            ② 트랩 발생 → mode switch
            
            ③ 커널 스택에 상태 저장
            
            ④ 트랩 핸들러로 가서 요청 처리, 다시 돌아옴(커널 스택에 있는 모든 것 pop해서 복원하고, 사용자 코드로 복귀)
            
    - 문2 해결: 타이머 인터럽트(HW 인터럽트)
        
        일정 시간 간격으로 mode switch
        
        - 협력적 접근: yield()나 그 외 시스템 콜 수행할 때마다 제어권 반환(할 때까지 기다릴게…) ⇒ 재부팅
        - 비협력적 접근: 타이머 인터럽트로 강제 반환 → 이제 스케줄러가 계속 CPU 줄지 다른 걸로 바꿔서 context switch 발생하게 할지 결정
3. 시스템콜 경로
    - 인자 전달 방식
        
        (1) 레지스터 전달
        
        (2) 메모리 블록/테이블 전달
        
        (3) 스택 전달
        
    - 함수 호출과의 비교
        
        공통은 jump뿐.. 권한 변화에서 차이 있음
        
    - 32bit vs 64bit
        
        
        | **int 0x80** | **syscall** |
        | --- | --- |
        | CPU가 IDT[0x80] 따라서 IDT 전체 조회 | CPU가 LSTAR의 kernel entry로 점프 |
        | 권한 검사, ring 0 stack(커널 스택) 전환 | 걍 레지스터에
        RCX ← 복귀주소, R11 ← RFLAGS |
        | 핸들러로 처리하고 iret | entry stub이 커널스택 전환 등등하고 sysret |
        
        ⇒ int 0x80: 범용 인터럽트 경로, syscall: 시스템콜 전용 지름길
        
        ⇒ syscall은 일반 인터럽트 경로 생략하고, 필요한 상태만 빠르게 넘김
        
        (나머지 스택 전환 같은 무거운 건 entry stub에 짬처리)

**대기와 조건 충족의 표현 (CV & Semaphore)**

Lock은 단순히 임계구역을 "보호(상호배제)"할 뿐, "원하는 조건이 될 때까지 기다리는 상황"을 표현하기에는 부족(어떤 조건을 만족할 때까지 기다리고 싶은데, lock만 쓸 때는 busy wait할 수밖에 없음. 락은 보호만 하지 알림 기능이 없으니까)

### **조건 변수 (Condition Variable, CV)**

- 대기 큐만 제공하며, 조건이 만족될 때까지 CPU를 낭비하지 않고 잠들게 함.
    
    → CV랑 같이 씀 ⇒ done이 상태를 기억, CV는 기다리는 스레드가 기다릴 공간 제공
    
    - parent(기다리는 쪽)
    
    ```c
    // 자기 할 거 하는 코드
    lock(&m);
    whlie(done == 0) // done = 0, 끝이 false 기다림
    	cond_wait(&cv, &m); // **lock 반납하면서** wait queue에 넣기
    	// 깨어나면서 락을 다시 잡음
    unlock(&m);
    ```
    
    ⇒ 이 cond_wait가 lock을 풀고 잠에 들기 때문에 두 가지 이슈 발생
    
    1. 깨어나서 ready 상태가 되어도 바로 임계구역에 진입하지 못하고 entry queue에서 lock을 잡기 위한 경쟁을 함
    2. 깨어나서 lock을 잡는 사이에 다른 스레드가 개입하여 조건을 무효화할 수 있으므로 whlie로 조건을 검사해야 함
    - child(끝내는 쪽)
    
    ```c
    // 자기 할 거 하는 코드
    lock(&m);
    done = 1; // 끝
    cond_signal(&cv); // OS가 하나의 스레드 깨움
    unlock(&m); // 락 해제
    ```
    
    - 실제 C코드(wait, signal에 pthread_붙이고 lock에는 pthread_mutex_붙이면 똑같음)
        
        ```c
        static pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER; 
        static pthread_cond_t cv = PTHREAD_COND_INITIALIZER; 
        static int done = 0;
        
        void *child(void *arg) { 
            /* do work ... */ 
            pthread_mutex_lock(&m); 
            done = 1; 
            pthread_cond_signal(&cv); 
            pthread_mutex_unlock(&m); 
            return NULL;
        }
        
        void wait_child_done(void) { 
            pthread_mutex_lock(&m); 
            while (done == 0)
                pthread_cond_wait(&cv, &m); 
            pthread_mutex_unlock(&m);
        }
        ```

- Mesa Semantics (signal을 보낸 스레드가 lock을 즉시 양보하지 않음): **`signal`**
    1. 조건이 참이라는 보장이 아니라, 잠든 스레드를 깨워 다시 검사할 기회를 줌. (OS 내부 문제로 알 수 없이 깨어나는 경우가 있어서 깨어났다 ≠ 조건이 참이다)
    2. 깨어난 스레드(ready 상태)가 락을 다시 잡는 사이 다른 스레드가 개입하여 조건을 무효화할 수 있음.
    - broadcast로 해도 모두가 깨어나지만 경쟁해서 락을 잡는 건 하나
- **While 루프의 필수성**: 위와 같은 이유 때문에, CV는 반드시 **`if`**가 아닌 **while 루프로 상태를 재검사** 해야 함
    
    ```c
    while(!ready) cond_wait(&cv, &m); 
    use(shared);
    ```
    
    1. **Signal을 보낸 스레드 (임계구역에 계속 머뭄)** 
    Signal을 보낸 스레드는 깨우는 신호만 전달할 뿐, 자신이 쥐고 있던 Lock을 깨어난 스레드에게 즉시 양보하지 않음. 즉, Signal 호출 후에도 자신이 명시적으로 **`unlock()`**을 호출할 때까지 해당 임계구역에서 남은 코드를 계속 실행.
    2. **Signal을 받은 스레드 (즉시 임계구역 진입 불가)** Signal을 받아 대기 큐(CV가 제공한 Wait Queue)에서 잠이 깬 스레드 역시 즉시 임계구역으로 진입(실행)하지 못함. 이 스레드는 Lock을 바로 넘겨받는 것이 아니라 entry queue**로 이동**하게 되며, Signal을 보낸 스레드가 Lock을 풀면 그때 다시 **Lock을 획득하기 위한 경쟁**을 치러야 함.

### **세마포어 (Semaphore)**

- 내부의 정수 카운터(**`value`**)와 대기 큐로 정의
- CV와 달리 허용량 자체를 **정수 값(토큰, 카운터)으로 기억**
- **동작**: (원자적 연산)
    
    
    | **sem_wait/wait** | count—, count가 부족하면 = 내가 진입할 수 없으면 잠듦 |
    | --- | --- |
    | **sem_post/signal** | count++, 이제 count 있으니까 기다리는 스레드가 있다면 깨움 |

    1. wait
        
        ```c
        wait(S) { // sem_wait, P(S)=시도
            S->value--; // 토큰 소비
            if (S->value < 0) { // 하나 있을 때 내가 까면서 들어가니까 0까지는 괜찮음
                add this thread to S->queue;
                block(); // 토큰이 부족하면 잠듦
            }
        }
        ```
        
    2. signal
        
        ```c
        signal(S) { // sem_post, V(S)=증가
            S->value++;
            if (S->value <= 0) {
                remove a thread T from S->queue;
                wakeup(T); // 기다리는 스레드가 있다면 깨움
            }
        }
        ```
        
    - value: 음수면 그 절댓값이 대기 중인 스레드 수, 양수면 남은 토큰 수
        
        ![세마포어 값과 두 스레드의 sem_wait/sem_post 흐름 예시 (OSTEP Figure 31.5: Thread Trace)](/assets/img/posts/OS_5_2/image-1.png){: width="400" height="295" }
        
- **용도**:
    - 0과 1만 가지는 **Binary semaphore**(락처럼 사용)
    - 허용된 자원 수를 관리하는 **Counting semaphore** ex. bounded buffer
    - 특정 사건의 발생 순서를 맞추는 **Ordering semaphore**
        
        ```c
        sem_t ready;
        int main() {
            sem_init(&ready, 0, 0); // 초기 토큰 0개, 가운데 0은 스레드 간 공유. 다른 숫자는 프로세스 간 공유
            // thread A, B 생성...
        }
        
        void A() {
            init_shared_state();
            sem_post(&ready); // 작업 완료 후 토큰 생성
        }
        
        void B() {
            sem_wait(&ready); // 토큰이 없으므로 A가 post할 때까지 잠듦
            use_shared_state();
        }
        ```
        

### Lock, CV랑 Semaphore 중 무엇을 선택?

- 그냥 상호배제만 보장 → lock
- join(parent가 child 종료 기다림)같이 어떤 스레드가 다른 스레드를 기다리는 상황 → 요구사항(ex. 자식이 끝났는지)을 확인해야 함 → CV + lock
- 여러 자원을 여럿에게 할당 → 남은 자원 수를 체크해야 함 → counting semaphore
- 카운터와 조건 확인 둘 다 필요 ex. bounded buffer → CV나 Semaphore + lock

### **고수준 추상화: 모니터 (Monitor)**

- Lock, CV, Semaphore는 여전히 상태 변수와 동기화 코드가 여러 곳에 흩어지거나, 개발자의 Wait/Signal 순서 실수로 오류가 발생하기 쉽다는 한계
- **모니터의 구조**:
    - **캡슐화**: 공유 상태(Shared data)와 관련 연산을 하나의 객체(클래스)로 묶어 외부의 직접 접근을 차단.
    - **자동 상호배제 (Entry Queue)**: 모니터 내부에는 한순간에 단 하나의 스레드만 활성화. 프로시저 진입 및 반환 시 자동으로 Mutex가 동작하여 Entry Queue를 관리. (mutex로 상호배제 보장하면서 entry queue에 넣음). entry queue는 mutex의 일부. lock을 다른 사람이 쥐고 있어서 기다리는 것. 이게 있어서 다수의 producer, consumer가 있을 수 있음.
    - **조건 대기 (Condition Queue)**: 요구사항이 맞지 않으면 **`wait()`**를 호출해 락을 내어놓고 자는 조건 대기줄(Condition Queue)을 따로 관리.
- Bounded Buffer Monitor 모델 ⇒ 그냥 함수 내부 전체!에 락을 건다고 봐도 됨(조건 확인부터)
    
    ```c
    item buf[N]; 
    int head, tail, count; 
    pthread_mutex_t m; // Entry Queue (상호배제용)
    pthread_cond_t not_full, not_empty; // Condition Queue (조건 대기용)
    // - not full은 꽉 안 찼을 때를 기다리고, not empty는 비어있지 않을 때를 기다림
    void put(item x) {
        pthread_mutex_lock(&m); // 1. 상호배제 획득 -> 여기서 막히면 entry queue
        while (count == N) {
            pthread_cond_wait(&not_full, &m); // 2. 공간이 없으면 대기 -> 여기서 막히면 condition queue=Wait queue
        } // m(lock)을 풀고 not_full 대기큐에 넣고 sleep.(여기서 signal도 받고, lock도 다시 얻어야 함수가 return되고 다음 문장 실행 가능)
        buf[tail] = x; 
        tail = (tail + 1) % N; 
        count++;
        pthread_cond_signal(&not_empty); // 3. 비어있지 않음을 알림
        pthread_mutex_unlock(&m); // 4. 상호배제 해제
    }
    
    item get(void) {
        pthread_mutex_lock(&m);
        while (count == 0) {
            pthread_cond_wait(&not_empty, &m);
        }
        item x = buf[head]; 
        head = (head + 1) % N; 
        count--;
        pthread_cond_signal(&not_full); // 공간이 생겼음을 알림 -> 시그널 받은 애는 block(condition queue)에서 ready 상태(entry queue)로.
        pthread_mutex_unlock(&m); // 이제 아까 시그널 받았던 애가 락을 얻기 위해 경쟁
        return x;
    }
    ```
    
- **결론**: 모니터는 프로그래머가 직접 락을 제어하는 부담을 줄이고, 동기화 정책을 안전하고 명확하게 관리할 수 있게 해주는 OOP 기반 동기화 추상화 기법. 외부에는 put, get만 호출.
    - 시나리오
        1. put 함수 내부에서 while (count == N) { 부분 검사 했더니 참임(가득 차 있음)
        2. pthread_cond_wait(&not_full, &m); 
        락을 풀고 not full이라는 condition queue에 이 스레드를 넣음. 상태는 waiting이 됨.
        3. 깨어남
            1. (정상) 락을 잡고 있던 스레드에서 signal을 보냄 pthread_cond_signal(&not_full); = not full에 있는 condition queue에 있는 스레드 중 하나에게 signal을 보냄 → 그 스레드가 깨면서 entry queue로 이동하고, 상태는 ready가 됨
            2. (비정상) OS 내부 문제로(알 수 없는 이유로) 잘못 깸
            
            이후는 상황 a에 해당한다고 가정
            
        4. 락을 잡고 있던 스레드에서 unlock을 함
        pthread_mutex_unlock(&m); → 깨어난 스레드가 락을 얻기 위해 경쟁(lock을 쥐어주는 건 OS 스케줄링에 따라 다름)
- CV, Monitor의 signal은 깨우기만 하고, 여기서 상태를 기억하는 건 상태변수임.
    - CV에서 상태 변수 없이 쓴다면?
        - ex. signal 보냈는데 그때는 안 기다렸으니까 신호 증발, 기다리는 애는 그때 보냈다는 걸 모르기 때문에 그냥 기다린다.
            
            ```c
            // [버그가 있는 잘못된 코드] 상태 변수(done)가 없는 상황
            
            // parent (기다리는쪽)
            lock(&m); 
            cond_wait(&cv, &m);  // 무조건 일단 기다림 (done 확인 안 함)
            unlock(&m);
            
            // child (끝내는쪽)
            lock(&m);
            cond_signal(&cv);    // 끝났다고 알림
            unlock(&m);
            ```
